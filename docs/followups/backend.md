### Contract changes from the BE-02 addendum (architecture hub and frontend)

- (a) `POST /auth/2fa/setup/start` and `/auth/2fa/setup/confirm` now require `currentPassword` (FU-BE-39).
- (b) New password-protected routes `POST /auth/2fa/disable` and `POST /auth/2fa/recovery-codes/regenerate` (body `{currentPassword}`; the first returns 204, the second `{recoveryCodes}`). The disable route is for roles that do not require 2FA; the UI should hide it for SUPER_ADMIN and REVIEWER.
- (c) New SUPER_ADMIN route `POST /auth/2fa/reset/:userId` (204; 400, 401 for a missing or invalid access token, 403, 404). Body `{currentPassword}` is the ADMIN's own current password (same shape as disable); a missing body is 400, a wrong or locked password 403 `REAUTH_FAILED`.
- (c3) Wrong or locked `currentPassword` on setup/start, setup/confirm, disable, regenerate and admin reset is now `403` problem+json with `code: 'REAUTH_FAILED'` and one fixed detail ("The current password is incorrect."), never 401, so the web app must not treat it as session expiry. `/auth/login` keeps its generic 401 and the 2FA code routes keep 400. The disable role refusal is also 403 but with `code: 'TWO_FACTOR_REQUIRED_FOR_ROLE'`, and only after the password check. The problem+json body gains an optional `code` member.
- (c2) Enrol and recovery-code responses now carry `Cache-Control: no-store`.
- (d) `/auth/2fa/verify` and `/auth/2fa/enroll/confirm` may return 503 "Verification is temporarily unavailable." when the replay store is down; the challenge stays usable, retry.
- (e) No 423 and no `lockedUntil` anywhere: on `/auth/login` a locked account is the generic 401, on the 2FA code routes 400 "That code is not valid.", and on the re-auth routes (setup, disable, regenerate, admin reset) 403 `REAUTH_FAILED` (FU-BE-22).
- (e2) For the architect and frontend: problem+json now has an optional `code` extension member (ADR 0001 C-9, QA-D-03 mock shape). Only our own coded 403s set it (`REAUTH_FAILED`, `TWO_FACTOR_REQUIRED_FOR_ROLE`), never a 5xx.
- (f) `apps/web/openapi/openapi.yaml` is a hand-written MSW mock contract (paths under `/v1`, not the real API), so it was NOT regenerated here: replacing it would be a huge unrelated diff and break the web mocks. The hub or frontend must swap it for `/api/docs-json` and delete the mocks (see its own header). apps/web was not edited.
- fsd.md API table (hub update): add `POST /auth/2fa/disable`, `POST /auth/2fa/recovery-codes/regenerate`, `POST /auth/2fa/reset/:userId` (SUPER_ADMIN) next to FU-BE-37's missing rows; audit actions `AUTH_2FA_DISABLED`, `AUTH_RECOVERY_CODES_REGENERATED`, `AUTH_2FA_RESET_BY_ADMIN`.

- **Step-up (review blocker B1, supersedes the earlier "unlock needs no password" decision).** Invite, PATCH (role, deactivate, reactivate) and unlock now need the admin's own `currentPassword` in the body, verified on the login path (`AuthService.verifyCurrentPassword` over `requireCurrentPassword`: reserve, equal work, shared lockout). A missing password is a `400`. The password is checked before the target is looked up, so the same-org `404` for a missing or other-org id appears only after a successful check. Re-checked inside the transaction (invite and unlock: plain read that the admin is still the active SUPER_ADMIN with the same hash, no admin row lock; role/deactivate: the admin rows the last-admin check already locks, in id order, include the caller's hash). This follows the FR-102 re-auth decision (FU-BE-39, FU-BE-46): a stolen SUPER_ADMIN access token alone cannot create a persistent SUPER_ADMIN, strip admins or unlock accounts repeatedly. Frontend: send `currentPassword` on `POST /admin/users`, `PATCH /admin/users/:userId` and `POST /admin/users/:userId/unlock`; the GET routes are unchanged. Self-unlock is allowed (with the password).
- Access tokens now die at a role change or deactivation for good (S1): a Redis marker `auth:tokens-valid-after:{userId}` (epoch seconds, TTL 20 minutes) is written inside the change transaction and the guard refuses an access token whose `iat` is at or before it, so deactivate then reactivate, or role A then B then A, does not revive an old token (a token issued in the same second as the change is refused too: sign in again. Access tokens are signed before the refresh family commits, and the change waits for that insert's row lock before writing the marker, so a racing sign-in's `iat` can never be later than the marker second; a +2 s lead on the marker was considered and not adopted: it is unnecessary on one clock and would refuse a sign-in made 1 s after the change, which QA's TC-004 expects to work. Multiple API instances need NTP sync, FU-BE-80). Redis down: the guard answers `503` 'Verification is temporarily unavailable.' and a role change or deactivation rolls back with the same 503. Existing `AUTH_PASSWORD_RESET` and `AUTH_ACCOUNT_LOCKED` unchanged. Every row has org, actor, entity (`user`), entity id (the target) and IP.

### Contract changes from the ADR 0011 follow-up (frontend and architecture hub)

ADR 0011 (owner decision C-21) answers 5 and 6 are now done on `POST /auth/2fa/disable` (FR-102, FR-104; TC-003). Answers 1 to 4 were done in BE-02. This supersedes FU-BE-44 where it says sessions are left alone.

### Contract changes from the client-error endpoint (frontend and DEP)

- New public route `POST /api/v1/client-errors` (owner decision C-32: CloudWatch only, no Sentry). No JWT or session needed (`@Public()` on purpose: candidates have no staff token and a crashed page may have no session). Response is `204` with no body. Errors are problem+json: `400` validation or malformed JSON (never echoes values), `408` slow body, `413` body over 16 KB, `415` compressed or non-JSON body, `429` rate limit.
- Body (JSON, `Content-Type: application/json`; no extra properties): `message` (required, max 1000), `stack` (max 8000), `name` (max 100), `url` (max 2000; the query string and fragment are dropped), `component` (max 200), `route` (max 200, use the route template, not the real URL), `release` (max 100), `level` (`error` or `warn`, default `error`). The user agent is read from the request header, not the body.
- Limits: own named throttler `client-errors`, `CLIENT_ERROR_THROTTLE_LIMIT` (default 10) per `THROTTLE_TTL_MS` (default 60 s) per IP (IPv6 bucketed by /64), plus `client-errors-global`, `CLIENT_ERROR_GLOBAL_LIMIT` (default 300) per window for the whole instance. Both are in memory and separate from default, auth and candidate. Body limit 16 KB, counted while streaming whatever the framing (no `Content-Length` needed, so no 411); a compressed body (`Content-Encoding` other than identity) and any non-`application/json` body (including a form post) are `415`; a body that takes longer than `CLIENT_ERROR_BODY_TIMEOUT_MS` (default 10 s) is `408`; malformed JSON, a non-object or an over-nested body (more than 20 levels) is `400`, and a request with no body is `400` from validation. Validation errors may name the attacker's own extra property names (the body is JSON the caller controls); they never echo values.
- For the Frontend: send from the global error boundary, `window.onerror` and `unhandledrejection`, always with `release` and `route`. Never put user data in a report (names, emails, answers, tokens, invite links, storage URLs); the server scrubs emails, JWTs, Bearer tokens, long opaque and hex tokens, OTP-looking numbers, presigned URL parameters, object keys, query strings, fragments and `password=` pairs, but that is a safety net: short unlabelled tokens (under 24 characters) are not caught (FU-BE-94). Debounce and cap reports per page load so the 10 per minute budget is not spent on one loop. A `sendBeacon` must use a Blob with type `application/json`. A failed report must never raise another report.
- For DEP: each report is one structured pino line on stdout with `event: "client_error"`, `reportedLevel` (`error` logs at error, `warn` at warn), `traceId` (the `x-request-id`), the scrubbed `message`, `stack`, `name`, `url`, `component`, `route`, `release` and `userAgent` (200 characters). No IP, headers or raw body are logged. It writes no audit row and touches neither the database nor Redis.
- QA: the route is listed `'public'` in `ROUTE_PERMISSIONS` (`POST /client-errors`); `apps/api/test/support/be03-routes.ts` is not edited by this change.
