### Contract changes from the BE-02 addendum (architecture hub and frontend)

- (a) `POST /auth/2fa/setup/start` and `/auth/2fa/setup/confirm` now require `currentPassword` (FU-BE-39).
- (b) New password-protected routes `POST /auth/2fa/disable` and `POST /auth/2fa/recovery-codes/regenerate` (body `{currentPassword}`; the first returns 204, the second `{recoveryCodes}`). The disable route is for roles that do not require 2FA; the UI should hide it for SUPER_ADMIN and REVIEWER.
- (c) New SUPER_ADMIN route `POST /auth/2fa/reset/:userId` (204; 400, 401 for a missing or invalid access token, 403, 404). Body `{currentPassword}` is the ADMIN's own current password (same shape as disable); a missing body is 400, a wrong or locked password 403 `REAUTH_FAILED`.
- (c3) Wrong or locked `currentPassword` on setup/start, setup/confirm, disable, regenerate and admin reset is now `403` problem+json with `code: 'REAUTH_FAILED'` and one fixed detail ("The current password is incorrect."), never 401, so the web app must not treat it as session expiry. `/auth/login` keeps its generic 401 and the 2FA code routes keep 400. The disable role refusal is also 403 but with `code: 'TWO_FACTOR_REQUIRED_FOR_ROLE'`, and only after the password check. The problem+json body gains an optional `code` member.
- (c2) Enrol and recovery-code responses now carry `Cache-Control: no-store`.
- (d) `/auth/2fa/verify` and `/auth/2fa/enroll/confirm` may return 503 "Verification is temporarily unavailable." when the replay store is down; the challenge stays usable, retry.
- (e) No 423 and no `lockedUntil` anywhere: on `/auth/login` a locked account is the generic 401, on the 2FA code routes 400 "That code is not valid.", and on the re-auth routes (setup, disable, regenerate, admin reset) 403 `REAUTH_FAILED` (FU-BE-22).
- (e2) For the architect and frontend: problem+json now has an optional `code` extension member (ADR 0001 C-9, QA-D-03 mock shape). Only our own coded 403s set it (`REAUTH_FAILED`, `TWO_FACTOR_REQUIRED_FOR_ROLE`), never a 5xx.
- (f) `apps/web/openapi/openapi.yaml` is a hand-written MSW mock contract (paths under `/v1`, not the real API), so it was NOT regenerated here: replacing it would be a huge unrelated diff and break the web mocks. The hub or frontend must swap it for `/api/docs-json` and delete the mocks (see its own header). apps/web was not edited.
- fsd.md API table (hub update): add `POST /auth/2fa/disable`, `POST /auth/2fa/recovery-codes/regenerate`, `POST /auth/2fa/reset/:userId` (SUPER_ADMIN) next to FU-BE-37's missing rows; audit actions `AUTH_2FA_DISABLED`, `AUTH_RECOVERY_CODES_REGENERATED`, `AUTH_2FA_RESET_BY_ADMIN`.

No `lastLoginAt`.
- Paths follow the web client (`/admin/users`, `{items}`, `name`), not `/users`. Deactivate and role change are one PATCH, as in the web mock; there is no separate deactivate route and no `GET /admin/users/:id`.
- Invite: 72 hour single-use token, only its SHA-256 stored, link `${WEB_ORIGIN}/admin/set-password#token=...` through mail template `staff-invite`. Accepted through the existing `POST /auth/password/reset` (FU-BE-49); no new public route. The invitee has `status: 'invited'` until the password is set.
- Mail templates (MailPort methods, no-op default until BE-06, FU-BE-50): `staff-invite` (`sendStaffInvite(to, inviteUrl)`) and `staff-account-locked` (`sendStaffAccountLocked(to, {email,name,minutes})`, sent to every active SUPER_ADMIN of the org with a password).
- Lock alert mechanism: the single place that writes the `AUTH_ACCOUNT_LOCKED` audit row also defers (setImmediate, same mechanism as forgot-password) an email to the org SUPER_ADMINs; failures are swallowed and logged by error name only. In-app alert: `GET /admin/users/lock-events` reads those audit rows (org scoped) and `locked` on `GET /admin/users`.
- **Step-up (review blocker B1, supersedes the earlier "unlock needs no password" decision).** Invite, PATCH (role, deactivate, reactivate) and unlock now need the admin's own `currentPassword` in the body, verified on the login path (`AuthService.verifyCurrentPassword` over `requireCurrentPassword`: reserve, equal work, shared lockout). Wrong, locked or changed-in-between all give the same `403` problem+json `code: 'REAUTH_FAILED'` with one fixed body (the web must not treat it as session expiry, as for the 2FA routes). A missing password is a `400`. The password is checked before the target is looked up, so the same-org `404` for a missing or other-org id appears only after a successful check. Re-checked inside the transaction (invite and unlock: plain read that the admin is still the active SUPER_ADMIN with the same hash, no admin row lock; role/deactivate: the admin rows the last-admin check already locks, in id order, include the caller's hash). This follows the FR-102 re-auth decision (FU-BE-39, FU-BE-46): a stolen SUPER_ADMIN access token alone cannot create a persistent SUPER_ADMIN, strip admins or unlock accounts repeatedly. Frontend: send `currentPassword` on `POST /admin/users`, `PATCH /admin/users/:userId` and `POST /admin/users/:userId/unlock`; the GET routes are unchanged. Self-unlock is allowed (with the password).
- Access tokens now die at a role change or deactivation for good (S1): a Redis marker `auth:tokens-valid-after:{userId}` (epoch seconds, TTL 20 minutes) is written inside the change transaction and the guard refuses an access token whose `iat` is at or before it, so deactivate then reactivate, or role A then B then A, does not revive an old token (a token issued in the same second as the change is refused too: sign in again). Redis down: the guard answers `503` 'Verification is temporarily unavailable.' and a role change or deactivation rolls back with the same 503. The admin 2FA reset sets it too, so the target's access tokens end at once (same rollback and 503 if Redis is down); this closes the 15-minute window of the earlier decision, and lets FU-BE-59 be closed when ADR PR #51 merges.
- Invites are limited per org and hour in Redis (`INVITE_RATE_LIMIT_PER_ORG_HOUR`, default 20): `429` when over, `503` when Redis is down. Deactivating a user with a password also clears a pending reset token (a pending invite keeps its token: the schema needs one, and acceptance requires an active user). List offsets deeper than 10000 rows are a 400.
- Audit action names written by BE-03: `USER_INVITED`, `USER_ROLE_CHANGED` (metadata `from,to,sessionsRevoked`), `USER_DEACTIVATED` (`sessionsRevoked`), `USER_REACTIVATED`, `USER_UNLOCKED` (`wasLocked`), `USER_LIST`, `USER_LOCK_EVENTS_LIST` (interceptor rows: metadata `{method, route}` only), `AUTH_INVITE_ACCEPTED`. Existing `AUTH_PASSWORD_RESET` and `AUTH_ACCOUNT_LOCKED` unchanged. Every row has org, actor, entity (`user`), entity id (the target) and IP.
- Problem responses also log (error level, name and trace id only) a missing org context and every 5xx. Raw SQL in `auth.service.ts` now also filters `org_id` (nil org for the nil-user path, so statement counts stay identical).
- Interceptor: `@Audited(action, entityType, { idParam })` in `apps/api/src/audit/audited.decorator.ts`; fails closed (500, no body) if the write fails or there is no staff user.
- Problem responses: a query that runs with no org context (OrgContextMissingError) is now `403` problem+json with the fixed detail `Access denied.` (was a defined 500); logged at error level by error name and traceId only. The DB PR #30 TC-008 fail-closed assertion was updated from 500 to this (assertion and the filter registration on its test app only).
- Guard: `JwtAuthGuard` is the single guard (no second RolesGuard); its user re-check runs in `runSystem('AUTH_BOOTSTRAP')`. A role change, deactivation or password change ends access tokens at once.
- Rules the web UI assumes (frontend.md BE-03 note) are implemented: no self role change or self deactivation (409), at least one active SUPER_ADMIN stays (409), deactivation revokes refresh tokens.
