### Contract changes from the BE-02 addendum (architecture hub and frontend)

- (a) `POST /auth/2fa/setup/start` and `/auth/2fa/setup/confirm` now require `currentPassword` (FU-BE-39).
- (b) New password-protected routes `POST /auth/2fa/disable` and `POST /auth/2fa/recovery-codes/regenerate` (body `{currentPassword}`; the first returns 204, the second `{recoveryCodes}`). The disable route is for roles that do not require 2FA; the UI should hide it for SUPER_ADMIN and REVIEWER.
- (c) New SUPER_ADMIN route `POST /auth/2fa/reset/:userId` (204; 400, 401 for a missing or invalid access token, 403, 404). Body `{currentPassword}` is the ADMIN's own current password (same shape as disable); a missing body is 400, a wrong or locked password 403 `REAUTH_FAILED`.
- (c3) Wrong or locked `currentPassword` on setup/start, setup/confirm, disable, regenerate and admin reset is now `403` problem+json with `code: 'REAUTH_FAILED'` and one fixed detail ("The current password is incorrect."), never 401, so the web app must not treat it as session expiry. `/auth/login` keeps its generic 401 and the 2FA code routes keep 400. The disable role refusal is also 403 but with `code: 'TWO_FACTOR_REQUIRED_FOR_ROLE'`, and only after the password check. The problem+json body gains an optional `code` member.
- (c2) Enrol and recovery-code responses now carry `Cache-Control: no-store`.
- (d) `/auth/2fa/verify` and `/auth/2fa/enroll/confirm` may return 503 "Verification is temporarily unavailable." when the replay store is down; the challenge stays usable, retry.
- (e) No 423 and no `lockedUntil` anywhere: on `/auth/login` a locked account is the generic 401, on the 2FA code routes 400 "That code is not valid.", and on the re-auth routes (setup, disable, regenerate, admin reset) 403 `REAUTH_FAILED` (FU-BE-22).
- (e2) For the architect and frontend: problem+json now has an optional `code` extension member (ADR 0001 C-9, QA-D-03 mock shape). Only our own coded 403s set it (`REAUTH_FAILED`, `TWO_FACTOR_REQUIRED_FOR_ROLE`), never a 5xx.
- (f) `apps/web/openapi/openapi.yaml` is a hand-written MSW mock contract (paths under `/v1`, not the real API), so it was NOT regenerated here: replacing it would be a huge unrelated diff and break the web mocks. A missing password is a `400`. The password is checked before the target is looked up, so the same-org `404` for a missing or other-org id appears only after a successful check. Re-checked inside the transaction (invite and unlock: plain read that the admin is still the active SUPER_ADMIN with the same hash, no admin row lock; role/deactivate: the admin rows the last-admin check already locks, in id order, include the caller's hash). This follows the FR-102 re-auth decision (FU-BE-39, FU-BE-46): a stolen SUPER_ADMIN access token alone cannot create a persistent SUPER_ADMIN, strip admins or unlock accounts repeatedly. Access tokens are signed before the refresh family commits, and the change waits for that insert's row lock before writing the marker, so a racing sign-in's `iat` can never be later than the marker second; a +2 s lead on the marker was considered and not adopted: it is unnecessary on one clock and would refuse a sign-in made 1 s after the change, which QA's TC-004 expects to work. List offsets deeper than 10000 rows are a 400.

### Contract changes from the ADR 0011 follow-up (frontend and architecture hub)

ADR 0011 (owner decision C-21) answers 5 and 6 are now done on `POST /auth/2fa/disable` (FR-102, FR-104; TC-003). Answers 1 to 4 were done in BE-02. This supersedes FU-BE-44 where it says sessions are left alone.

- Body is `{ currentPassword, totpCode }`. `totpCode` is a 6-digit TOTP code only; a recovery code or a missing code is 400. The frontend must collect a TOTP code next to the password.
- Order: password (403 `REAUTH_FAILED`), 409 if 2FA is off, TOTP code (same 403 `REAUTH_FAILED` body for a wrong or replayed code; counts toward the same 5-attempt lockout; Redis outage is 503 "Verification is temporarily unavailable." and counts nothing), then the role refusal 403 `TWO_FACTOR_REQUIRED_FOR_ROLE` for SUPER_ADMIN and REVIEWER. The 409 before the code check tells a caller who already holds the password only that 2FA is off.
- Success is still 204 but now signs the user out everywhere: every refresh-token family of the user (including the caller's) is revoked in the same transaction that clears the TOTP secret, flag and recovery hashes, and the response clears the refresh cookie. The frontend must redirect to sign-in after a successful disable. The audit row `AUTH_2FA_DISABLED` carries `{ sessionsRevoked }`.
- Access tokens issued before a disable now end at once through the BE-03 tokens-valid-after marker (FU-BE-59). `POST /auth/2fa/reset/:userId` already revoked all of the target's families (answer 5) and keeps its test.
- QA-owned `apps/api/test/integration/tc-003.int.test.ts` already sends `totpCode` to `/2fa/disable` (updated by QA).
