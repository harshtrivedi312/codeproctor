## frontend/step-3 session follow-ups (for backend and later web work)

- **[BE-02] `POST /v1/auth/logout` must be idempotent and revoke by the httpOnly refresh cookie alone.** Answer 204 when the cookie is missing, expired or already revoked, and do not require an access token: after a failed logout the web retries it on the next page load with no access token. Logout with a rotated or reused refresh token must revoke the WHOLE token family (TC-005 reuse detection); otherwise treating a 401 from logout as confirmed is unsafe, because a stolen older token could still be live. ## frontend/sync-questions-192 (revision returned from question-bank writes, FU-BE-151 / Q4)

Read from the real change (commit 42b0526e, `questions.service.ts`, `variants.service.ts`, `question-tx.ts` `currentRevision`, the DTOs and the e2e specs).

**What the API does now (the web follows it exactly):** every content write answers the revision computed AFTER the mutation, inside the same transaction and under the question row lock (writers only): content `PATCH /questions/{id}` answers the detail plus a top-level `revision` (the revision of the version the edit left, the new version after a fork; it equals `version.revision`); test-case POST (201) and PATCH answer the test case plus `revision`; variant POST and PATCH answer `{variant, revision}` (now also re-read in the transaction); the override PUT answers the override plus `revision`; the three DELETEs (test case, variant, override) answer **200 `{revision}` instead of 204**. Status codes and the order of checks are unchanged. Publish, archive, unarchive, validate and the AI routes are unchanged (no revision).

**Why dropping the read-back is safe:** the revision a write returns is the state after that write and after everything committed before it (the question row lock serialises writers). A change by another editor committed before our write fails that write's own `expectedRevision` check (409). A change committed after our write A and before our write B leaves the server revision different from the one A answered, and B carries A's answer, so B is a 409: fail closed, nothing further is sent, their change is intact. The answer to A cannot contain their change, so it can never be adopted by mistake. The only thing that cannot tell the difference is an edit and its exact undo by another editor (same content, same revision), which changes nothing.

**Changed on the web:**

- `saveQuestion` chains the RETURNED revision of every write (variant PATCH/POST, content PATCH, test-case POST/PATCH/DELETE, variant DELETE, override PUT/DELETE). Removed: the read-back GET after every test-case, override and variant-delete write, `slotsSignature`, `contentSignature`, the expected-state builders and the false-409 risk of comparing server-normalised text. A save is now N writes plus one final read (for the server's own ids), where it was 2N plus one.
- Kept: the partial-save logic (`PartialSaveFailure`, `lastRevision`, `resync`). `lastRevision` is now the last answered revision; the editor adopts the server's revision for a retry only when a fresh read has exactly that revision (so a write that failed without an answer and was applied after all, or anyone else's write, makes it a reload). A 409 mid-save still says part was saved and keeps the edits.
- Mocks (`question-handlers.ts`) and `openapi.yaml` (`RevisionResult`, `TestCaseMutation`, `VariantOverrideMutation`, `QuestionUpdateResult`) answer these shapes; `gen:api` rerun.
- Tests: B2 and the content-field tests now prove the 409 on the next write when another editor commits in between (title, test case), a save is N writes plus one read, the routes answer the right revision (equal to the next GET), and the three DELETEs are 200.

**Closed:** Q4 and FU-BE-151 (revision from the transaction); the "residual window" of the content PATCH answer (B2, nit 1) and nits 2 and 3 on `contentSignature` (the code is gone).

## frontend/busy-retry (503 BUSY handling, DL-37; read from problem.filter.ts, coded.exception.ts, api-contract section 8, ADR 0013 5.7)

**Built**

- One mechanism in the shared staff API client (`src/lib/api/client.ts` middleware, rules in `src/lib/api/busy.ts`): a 503 whose problem body has code BUSY (a clone is parsed) is sent again up to 3 more times (4 attempts), after `Retry-After` clamped to 1..5 s (missing or unusable: 1 s) plus up to 0.4 s jitter, and the retries stop once the next wait would pass about 10 s in all. Anything else is passed through untouched: any other 503 (for example the Redis outage), any 500, any other status.
- Safety: the request is cloned before the first send (a body that cannot be cloned is not retried); the retry carries the session generation stamp of the original call and stops if the generation, user or role changed (never a request for another person), or if the call's `AbortSignal` aborted (list queries now pass TanStack's `signal`, so leaving the page cancels the wait). A call can opt out with the `x-cp-no-busy-retry` header (removed before sending). Candidate routes (`/v1/candidate/*`) are never retried by this client (see `isNoRetryRoute`); the real candidate flow sends through the proctor SDK's own buffer.
- Silent refresh (`auth-session.ts`): the same bounded retry before concluding anything. A 503 BUSY that persists does NOT sign the user out and publishes nothing: `refreshBusy` is raised, `RequireRole` shows a calm "We did not sign you out" with Try again on first load. 401, 403 and any other failure still sign out as before.
- UX: `BusyNotice` (in the staff shell, a polite `role=status` region that always exists): "The service is busy; trying again…" while waiting; "Still busy. Wait a moment and try again." with Try again (reloads the failed lists) after the retries run out; and, after a 500 on a staff write, "Something went wrong. Check before trying again: look at the list or the status first, because the action may already have happened." TanStack: queries do not retry a BUSY (`shouldRetryQuery`), one retry for other read failures, mutations never retry. Call sites: `writeFailureText` (users page), the question editor (BUSY and 500 messages; a 500 inside the save chain is a `PartialSaveFailure` that says the step "may have gone through as well" and keeps the revision-checked retry), and the bulk CSV upload (a 5xx chunk "may have been sent").

## frontend/single-flight-refresh (cross-tab refresh, unknown-outcome 500; api-contract section 8)

**Built**

- Cross-tab single flight for `POST /v1/auth/refresh` (`src/lib/refresh-coordination.ts`, used by `auth-session.ts`): Web Locks `cp.refresh`; the winner sends the request and broadcasts its outcome over a BroadcastChannel before it releases the lock; a tab that waited for the lock reuses that outcome and sends nothing (short grace for message lag; if no outcome comes, the holder is presumed gone and the tab sends its own). Fallback without Web Locks: a BroadcastChannel start-announcement election (lowest random id sends). With neither, only the in-tab single flight remains.
- Decision: the winner broadcasts the outcome including the new access token and session user (option a), memory only. A bare "done" signal cannot work with an in-memory token and a forbidden second refresh. A tab keeps a received outcome only while its own refresh is waiting; every other message is dropped on arrival. The result still goes through the generation, user-id and sign-out-marker guards. Nothing is written to any storage or cookie (test asserts it).
- The five unknown-outcome routes (setup/confirm, enroll/confirm, disable, recovery-code verify, staff invite): fixed message, never retried, per-route recovery (see PR). Mock support: `setMockOutcomeUnknown({ route, methods, count, landed })` in `fault-handlers.ts`. _(Obsolete after the merge of D-70: forced enrolment and its `enroll/*` routes are gone; the setup/confirm unknown outcome now signs out to `?reason=two-factor-unconfirmed`.)_
