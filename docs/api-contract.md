# API contract (ARC-02)

Authoritative REST contract (ADR 0001 C-8). BE-01 exists, so a route moves to the code-first OpenAPI once the backend publishes it there and ARC-02 part 2 confirms it matches; until then this file wins. Paths follow the backend's routes under `/api/v1`; ARC-02 part 2 settles the remaining paths, adds the other endpoint groups and the fsd.md §4 rows.

Errors are RFC 7807 problem details (ADR 0001 C-9, as implemented in `problem.filter.ts`: `type`, `title`, `status`, `detail`, `instance`, `traceId`, `errors`). This contract adds two extension members: **`code`** (a stable machine-readable string such as `REAUTH_FAILED`) and, on candidate routes only, **`sessionStatus`** (section 4). `ProblemDetails` in `apps/api/src/common/problem.filter.ts` carries an optional `code` (already on main). `code` is set only where this contract names one: `REAUTH_FAILED` (the `PROBLEM_CODES` in backend PR #26), `SETTINGS_CONFLICT` (section 2) and `VARIANT_HAS_AI_REFERENCES` (section 5), `BUSY` (section 8: lock contention answers 503 on every route except refresh and the unknown-outcome routes at commit), `REASON_NOT_ENABLED` (ADR 0015 section 6, "API, locking, access and audit": a 422 on `POST /tests/:id/invitations` and the accommodations `PATCH` when the waiver reason `REFUSED_BIOMETRIC_PROCESSING` is switched off by the server flag), and `ANSWER_NOT_MANUAL`, `SESSION_NOT_UNDER_REVIEW` and `VERDICT_ALREADY_SET` (section 7). Candidate-route codes such as `SESSION_NOT_ACTIVE` come from ADR 0013 section 5.1. Guard 403s (role or permission denial) carry no `code`. Clients branch on `code`, never on `detail` text. Codes named by an accepted ADR (ADR 0013 section 5.1, ADR 0015) count as named too. **Code lists in the API (decision for FU-FE and #245's drift test):** `PROBLEM_CODES` is the general list for every route, staff and candidate, and will hold `BUSY` and `REASON_NOT_ENABLED` as well as the staff codes above (Backend adds them to `coded.exception.ts`; neither is there yet); `CANDIDATE_PROBLEM_CODES` holds only the codes that exist on candidate routes (such as `SESSION_NOT_ACTIVE`, `TOKEN_EXPIRED`, `SESSION_TAKEN_OVER`) and `BUSY` also applies there through the global filter, so it stays in `PROBLEM_CODES` and is not repeated in the candidate list. There is no third list. ADR 0015's codes are assigned as follows: `PROBLEM_CODES` holds `REASON_NOT_ENABLED`, `ACCOMMODATION_LOCKED`, `IDENTITY_NOT_WAIVED`, `PRECONDITION_FAILED` and `PRECONDITION_REQUIRED` (staff routes), and `CANDIDATE_PROBLEM_CODES` holds `IDENTITY_CHECK_WAIVED` and `DETECTOR_DISABLED` (candidate routes).

## 1. Re-authentication for 2FA management

Owner decisions (C-21, 2026-10-05, D-49; ADR 0011, Accepted): `currentPassword` is required on 2FA setup, disable and recovery-code regeneration; a wrong password returns 403 `REAUTH_FAILED`; forced enrolment is unchanged; the six answers are recorded below. **Amended by D-70 (2026-10-08, the owner):** TOTP is optional for every role, so forced enrolment at login and the role refusal on `POST /auth/2fa/disable` are retired (see the notes under the table); the re-auth rules stand. Rules marked **(architect detail)** were added by the architecture hub to make the decision implementable and are covered by C-21's acceptance of ADR 0011.

### Endpoints

| Method and path                                         | Who                                                  | Body                                     | Success                                                            |
| ------------------------------------------------------- | ---------------------------------------------------- | ---------------------------------------- | ------------------------------------------------------------------ |
| `POST /auth/2fa/setup/start`                            | Any staff, signed in                                 | `{ currentPassword }`                    | 200, otpauth URI, manual key and `qrDataUrl`                                    |
| `POST /auth/2fa/setup/confirm`                          | Any staff, signed in                                 | `{ currentPassword, code }`              | 200, the 10 recovery codes, shown once. Since D-70: revokes all of the user's refresh sessions, the caller's included, sets the access-token revocation marker and clears the refresh cookie; the UI shows the codes, then calls `POST /auth/logout` and goes to sign-in |
| `POST /auth/2fa/disable` | Any signed-in staff with 2FA on (409 if off); since D-70 no role is refused (the 403 `TWO_FACTOR_REQUIRED_FOR_ROLE` of C-21 is retired) | `{ currentPassword, totpCode }` (`totpCode`: a current 6-digit TOTP code, never a recovery code (decided by the Delivery Lead, DL-15, as within C-21's "a current 2FA code"; a user who lost their device turns 2FA off through an admin reset); **backend PR #51, pending merge**; until it lands send only `currentPassword`: main runs with `forbidNonWhitelisted`, so an unknown `totpCode` field is a 400) | 204. **After #51 (pending):** revokes all of the user's refresh sessions, the caller's included, and clears the refresh cookie. **On main:** revokes nothing and leaves the cookie. Either way the UI calls `POST /auth/logout`, then goes to sign-in |
| `POST /auth/2fa/recovery-codes/regenerate`              | Staff with 2FA on (409 if off) **(architect detail)** | `{ currentPassword }`                    | 200, 10 new codes; the old ones stop working                       |
| `POST /auth/2fa/reset/:userId` (C-21)                    | SUPER_ADMIN, same organisation; not for the caller's own account (400, checked before the password) | `{ currentPassword }` (the admin's own)  | 204; an unknown or other-organisation `userId` is 404 (ADR 0006); revokes the target's refresh sessions |

The paths are the routes on main (backend #26); ARC-02 part 2 pins them in fsd.md §4.

### Rules

- `currentPassword`: a string of 1 to `MAX_PASSWORD_LENGTH` characters, the same bound as login; never trimmed or normalised **(architect detail)**.
- **Wrong password: HTTP 403, problem `code: "REAUTH_FAILED"`**, `detail` "The current password is incorrect." on every route **except `POST /auth/2fa/disable`** (Backend A #184, FU-BE-144), which answers one fixed `detail` "The password or code is incorrect." for a wrong password, a wrong or replayed TOTP code, a password changed mid-request and a locked account alike (a missing or malformed `totpCode` stays a 400 from body validation), so the response does not reveal which factor failed. It is not 401: the session is valid, and a 401 means "access token expired" to the client (it would refresh and retry).
- **Locked account (architect detail).** While `locked_until` is in the future, the check burns an Argon2 verify and returns the identical 403 `REAUTH_FAILED` even for the correct password, so a locked account gives no signal and the route cannot be used to keep guessing. Wrong attempts count towards the same lockout as login (FR-101, TC-002); the failure that triggers the lock writes the same account-locked audit row as login. On main a successful re-auth does not reset the failed-login counter; it only gives back its own attempt reservation (BE-02 may confirm or change this).
- Check order (as implemented in #26): authentication and role guard (a role or permission denial is a plain 403 with no `code`), then body validation and path validation (400, including a UUID check and, for reset, a self-target which is 400), then the password (403 `REAUTH_FAILED` when wrong or locked), then the remaining checks; **for `disable` as implemented in #51**: password, then 409 if 2FA is off, then the TOTP code (wrong or replayed code: 403 `REAUTH_FAILED`, same body as a wrong password, counted toward the same lockout), then the role refusal (retired by D-70; in #51 it came last, so a SUPER_ADMIN or REVIEWER must give a valid code before hearing "required for your role"; on main it comes right after the password). A missing or malformed `totpCode`, or a recovery code in its place, is a 400 from body validation, before the password check; **for `disable` as in #26 (until #51 merges)**: (retired by D-70) a role whose 2FA is mandatory gets 403 `TWO_FACTOR_REQUIRED_FOR_ROLE` (after the password, so it is not revealed without it); the 409 when regenerate or disable is called with 2FA off is also after the password and is not a guard; an unknown or other-organisation reset target is 404. A wrong TOTP `code` on setup/confirm after a correct password is the ordinary 2FA validation error (400 "That code is not valid."), not `REAUTH_FAILED`; on main it also counts toward the lockout: the 400 applies to the wrong code itself (including the one that triggers the lock), while a locked account is refused earlier, at the password check, with 403 `REAUTH_FAILED` (`requireCurrentPassword` runs first, so a locked account on setup/confirm gets 403 `REAUTH_FAILED`, not 400).
- Every re-auth success and failure is audited: who, which action, outcome, never the password **(architect detail; required, not fully on main: today only the completed actions are audited (`AUTH_TOTP_ENABLED`, `AUTH_2FA_DISABLED`, `AUTH_RECOVERY_CODES_REGENERATED`, `AUTH_2FA_RESET_BY_ADMIN`) and the failure that triggers the lock; a failed re-auth otherwise and a successful `setup/start` write no audit row: backend follow-up)**.
- `currentPassword`, `password` and `newPassword` must be on the API's pino redact list as defence in depth (`req.body.currentPassword`, `req.body.password`, `req.body.newPassword`, and the same under any logged error context), and validation errors must never echo submitted values. **On main:** `apps/api/src/common/log-redaction.ts` redacts `currentPassword`, `password` and `newPassword` (hub-checked 2026-10-06).
- **A stale forced-enrolment challenge:** `POST /auth/2fa/enroll/start` and `POST /auth/2fa/enroll/confirm` answer 401 with `detail` "Your sign-in has expired. Sign in again." when the challenge token is expired or no longer valid (Backend A #184), not 409 for a password change or deactivation that races the request.
- **Forced enrolment is retired (D-70).** Login will no longer return an enrolment challenge once the Backend A and Frontend A code PR lands, because no role has mandatory TOTP; until then the flow below still runs, and the text of this bullet describes it as it stood. Backend A removes the `/auth/2fa/enroll/*` routes, the role-keyed checks on login and refresh (`TOTP_REQUIRED_ROLES`), and the 403 `TWO_FACTOR_REQUIRED_FOR_ROLE` together with its entries in `PROBLEM_CODES`, the web enum and the preamble above in one PR with Frontend A (the web drift test compares the enum with the preamble, so all must change together). **Kept (D-70):** a user with TOTP enrolled is asked for the code at every sign-in and is never signed in without it, whichever path (a recovery code counts as the second factor; nothing else replaces it). Because a user may enrol while password-only refresh sessions are open, a successful `POST /auth/2fa/setup/confirm` revokes ALL of the user's refresh families in the same transaction, the caller's included, sets the same Redis access-token revocation marker that `disable` and the role-change PATCH set (so an access token issued before enrolment, for example one held by someone who stole the password, stops working at once and not only when it expires; a Redis outage rolls the confirm back with a 503, as for PATCH), and clears the refresh cookie, exactly like `disable` (an access token carries no refresh-family id, so the caller's own family cannot be told from the others). The UI shows the recovery codes, then calls `POST /auth/logout` and goes to sign-in, which now asks for the TOTP code. A session opened before enrolment, for example one held by someone who stole the password, therefore does not outlive the moment the user turns on TOTP. The revocation count is written to the audit row. (Whether the account holder also gets an email when 2FA is enabled, disabled or reset is an open product question for the owner, not decided here.) An admin reset of someone's 2FA (`POST /auth/2fa/reset/:userId`) returns that account to password-only sign-in, which the UI warns the admin about. Roles whose TOTP was mandatory (FR-102) enrolled during login through the challenge-token flow (`/auth/2fa/enroll/start` and `/confirm` with `challengeToken`), which already follows a password check. It takes no `currentPassword` and issues no access token until enrolment is confirmed (TC-003).

### Owner answers (C-21, 2026-10-05, D-49)

1. A SUPER_ADMIN reset needs the admin's own password. Matches #26.
2. Re-auth failures share the login lockout (five wrong attempts lock login for 15 minutes). Trade-off noted: someone holding a stolen access token can lock the real user out repeatedly; an anonymous attacker who knows the email can already do that, so there is no new exposure. Matches #26.
3. (Retired by D-70.) Mandatory-2FA roles (SUPER_ADMIN, REVIEWER) could not disable 2FA: 403 `TWO_FACTOR_REQUIRED_FOR_ROLE`, checked after the password (matched #26). Any role can now disable with the password and a current code.
4. An admin can reset another admin's 2FA but not their own: a self-reset is 400, checked before the password. Matches #26.
5. Disabling or resetting 2FA revokes that user's sessions. Reset already revokes the target's refresh-token families in #26; disable revokes them too (backend PR #51, pending merge; until then a disable does not revoke). Access tokens already issued expire within 15 minutes, so this is not an immediate compromise response.
6. Disabling 2FA also needs a current TOTP code. `totpCode` is required in `{ currentPassword, totpCode }` (backend PR #51, pending merge; #26 requires only the password today).

### Account-holder notification (D-76; Backend A builds it after the demo, in its own PR)

The account holder gets an email whenever two-factor sign-in changes on their account.
- **Triggers (three, after the action has committed):** turned ON (`POST /auth/2fa/setup/confirm`, and the forced-enrolment confirm while that route still exists), turned OFF (`POST /auth/2fa/disable`) and RESET (`POST /auth/2fa/reset/:userId`, the admin reset, only when the target had 2FA on: a reset of an account whose 2FA was already off changes nothing and sends nothing; nothing is sent to a deactivated target). No other route sends it; recovery-code regeneration deliberately sends no mail.
- **Recipient:** the account holder's own address, read from the user row of the account whose 2FA changed. For an admin reset that is the target user, read inside the reset transaction and never the admin. No copy goes to anyone else.
- **Timing and failure:** the mail is queued on the existing mail service after the action's transaction has committed (queued path, not inline). A failed or refused enqueue (queue full, stopped, any error) never changes the response, the status code or the stored state, and never rolls anything back; it is logged by error name and template only. "Queued" means the in-process queue accepted the job, not that it was delivered.
- **Audit row for the outcome:** a separate audit row, action `AUTH_2FA_NOTICE`, entity type `user`, entity id the account holder, actor the admin for a reset and the account holder otherwise, written in the route's own scope, with metadata `{ template, outcome: 'queued' | 'failed' }` and no address. It is written directly, not through `@Audited` or the interceptor. If writing it fails, the response still does not change: this row is exempt from the fixed 500 of the post-commit audit carve-out in section 8 on all four routes; the failure is logged at error level with the error name and the audit action only and raises the same metric as that carve-out.
- **When no mail is sent:** the action failed, rolled back, or is the reset of an account without 2FA. After a commit-time P2028 on the reset route (503 `BUSY`, section 8) no mail goes out until the admin retries. After the unknown-outcome 500 (FU-BE-208) on setup/confirm or disable the mail cannot be sent for certain; for disable, where a silent turn-off hides a takeover, Backend uses the `FOR UPDATE` re-read section 8 permits and sends the mail if it shows the change committed (otherwise the gap is accepted and recorded).
- **Templates (fixed, no free text):** template ids `two-factor-enabled`, `two-factor-disabled` and `two-factor-reset`, with the fixed subjects "Two-factor sign-in was turned on for your account", "Two-factor sign-in was turned off for your account" and "Two-factor sign-in was reset on your account". Params: only `occurredAt`, the server time right after the commit, rendered with the existing `when()` helper ("YYYY-MM-DD HH:MM UTC"). Bodies: `two-factor-enabled` says what changed and when, and says nothing about sessions (turning 2FA on revokes none of the account's sessions, apart from what the confirm rule above does); `two-factor-disabled` and `two-factor-reset` also say that every session of the account, the current one included, was signed out. All three say that if it was not the account holder they should contact their administrator and change their password; a reset says "an administrator" and names no one. No code, key, secret, recovery code, link, recruiter or admin name, organisation free text or user-supplied text appears, and there is a plain-text part like the other templates.
- **Limits:** only the global throttle bounds the mail count (the re-authentication limits count failures only). Someone cycling their own 2FA on and off mails only themselves, and a repeated reset of the same account is removed by the rule above.
- **No oracle:** every trigger runs only after the password (and for disable a current code) has been verified, so the mail reveals nothing to an unauthenticated caller.
- **Tests (QA assigns TC IDs):** each trigger enqueues exactly one job with the right template and recipient, and the params hold only `occurredAt`; an admin reset mails the target, not the admin; a reset of an account without 2FA and of a deactivated target sends nothing; a failed enqueue leaves the response and the 2FA state exactly as without the failure, and a failed notification audit write does too (logged and counted); no log line or audit row contains the address, a code, a key, a secret or a recovery code (planted-value scan); no mail after a wrong password, a rollback or a 503; the enabled mail does not mention sessions and the other two do.

### Frontend (Security page)

- After a successful `disable` (204), always call `POST /auth/logout` and then go to sign-in. **On main (before #51 merges)** disable revokes nothing and leaves the `cp_refresh` cookie valid, so clearing client memory alone would let the next page load refresh silently; the logout call revokes the caller's family and clears the cookie, and is harmless after #51 (which signs the user out everywhere itself). Access tokens already issued live up to 15 minutes (FU-BE-59).
- Setup: one password prompt that keeps the password in component state from `start` through `confirm`; clear it on confirm, error or close. Disable and regenerate: a prompt per action.
- On 403 with `code: "REAUTH_FAILED"` show "Password is incorrect" inline (for `disable` after #51 show "Password or code is incorrect": the body deliberately does not say which) and keep the dialog open; do not sign out and do not refresh. `TWO_FACTOR_REQUIRED_FOR_ROLE` is retired by D-70: show the disable control for every role that has 2FA on; any other 403 is a permission problem, not a password problem.
- The bearer-authenticated routes (`/auth/2fa/setup/*`, `disable`, `recovery-codes/regenerate`, `reset`) must not count as auth requests in `isAuthRequest`, so that a real 401 (expired access token while the dialog is open) refreshes and retries once. The challenge-token routes (`/auth/2fa/enroll/*`, `/auth/2fa/verify`), login, refresh and logout stay excluded. The retry copy of the request (it carries `currentPassword`) must be dropped when the retry settles; the password stays in memory only, never in storage. Today every `/v1/auth/*` path is excluded from refresh.

### Session user: `totpEnabled` (Delivery Lead decision, hub conditions)

**Not on main yet: backend follow-up (owner: backend-engineer, task to be assigned by the Delivery Lead), pending.** `AuthUserDto` today is `{ id, email, name, role, orgName }` (`apps/api/src/auth/dto/auth.dto.ts`). It will gain `totpEnabled: boolean`, returned wherever an authenticated session user is returned (a completed login, `2fa/verify`, enrol confirm, `refresh`). There is no `GET /auth/2fa/status` route. Until the backend change lands the field is `undefined`: Frontend must treat `undefined` as unknown, must not render an "Enable 2FA" call to action from it, and shows the Security page without the on/off state (setup/start answers 409 when 2FA is already on). The web reads the flag from the session user and, after setup/confirm (which returns no session user), sets it to `true` locally on the 200 and, since D-70, setup/confirm signs the user out as disable does (all refresh families are revoked), so the next sign-in returns the flag; disable signs the user out, so no re-read is needed there. Conditions: it appears only in responses that already carry an authenticated session user, never in the pre-2FA login responses (`two_factor_required`, enrolment required) or any unauthenticated response; it describes the caller's own account only; it is output only (never accepted in a request body); it is never put into access-token claims, so a stale JWT cannot carry it; a stale value never grants anything because the server checks the real state on every re-auth route. `packages/shared` has no session-user schema today (no `orgName` there either); if one is added it carries the same field (a shared-contract change through the hub).

### Tests (QA assigns new TC IDs for re-auth; TC-002 and TC-003 are cited only for the lockout regression, and TC-003 for optional 2FA, D-70)

FR-102, FR-101, TC-002, TC-003: wrong password is 403 `REAUTH_FAILED` on each endpoint; correct password succeeds; repeated wrong passwords lock; a locked account with the correct password still gets 403 `REAUTH_FAILED`; a role denial carries no `code`; disable by any role succeeds with the password and a current code, and 409 when 2FA is off; a user with TOTP enrolled is never signed in by password alone, password reset, refresh or any other path without the second factor, and `setup/confirm` revokes all of the user's refresh families, the caller's included, clears the cookie, sets the Redis access-token revocation marker inside the same transaction (so an access token issued before enrolment stops working at once, as after disable) and writes the revocation count to the audit row (D-70 retires forced enrolment and the 403 `TWO_FACTOR_REQUIRED_FOR_ROLE`); a self-reset is 400 before the password; reset revokes the target's refresh sessions; disable without a current TOTP code is refused once the backend follow-up lands; the password never appears in logs or audit records.

## 2. Organisation settings (BE-04c follow-up; FU-BE-126)

Proposed by Backend A through the Delivery Lead (2026-10-06). The route shape is the hub's call (architect detail); the new FSD §4 row is the owner's. Settings live in `organizations.settings` (jsonb, database.md; shape `OrgSettings`).

| Method | Path | Role (permission) | Purpose |
| --- | --- | --- | --- |
| GET | `/admin/org-settings` | SUPER_ADMIN (`org_settings:manage`) | Read the effective settings of the caller's organisation, defaults applied. |
| PATCH | `/admin/org-settings` | SUPER_ADMIN (`org_settings:manage`) | Change one or more allowed keys. |

Rules:

- **Org scope:** the organisation comes from the access token. There is no org id in the path or body, and a body `orgId` is rejected as an unknown key. The service runs in the request's STAFF scope (`runAsUser`, set by `OrgContextInterceptor`; the org id is `ctx.orgId`). ADR 0006 section 8.6 allows an `organizations` update only there, through a top-level `organization.update` or `updateMany`; raw SQL never writes `organizations` (section 8.5).
- **Strict allowlist, at every nesting level:** an unknown key, at any depth (for example `aiReferences.refreshDays` today), a `null` for an object or value, and a wrong type are all 400 (problem details, `errors` names the key). A key joins the allowlist only by its owner's decision. Today:
  - `aiReferences.minAssistants`: integer 0..5, default 2 (ADR 0005 AI-5; 0 turns the publish gate off). **(architect detail)** ADR 0005 gives no maximum; the bound is 5. A stored value outside 0..5 or of the wrong type reads as the default 2, in GET and in the publish gate alike: both use one reader (the narrow reader in the "One reader, parsed narrowly" rule below, not the strict `orgSettingsSchema`), and a test checks that they agree for out-of-range stored values. The `MAX_MIN_ASSISTANTS = 10` in `apps/api/src/questions/ai-reference-rules.ts` must become 5.
  - Not yet allowed, each needing its owner's decision: `retention_days` (a column, not the jsonb), `aiReferences.refreshDays` (AI-4), risk weights, consent version, and every other `OrgSettings` key (ADR 0007 section 6: `erasure.holdWhileReviewOrAppealOpen`, `maxProctorPauseMinutes`, detector thresholds, `consentDeclineContact`).
  - Stored keys outside the allowlist are kept untouched by PATCH and are not returned by GET.
- **GET response (200):** `{ "aiReferences": { "minAssistants": 2, "isDefault": true } }`, always with every allowed key present (defaults applied); `isDefault` is true when no valid value is stored and the default applies (as built in #165; `orgSettingsViewSchema` in `packages/shared`). Send `Cache-Control: no-store`.
- **PATCH body:** `currentPassword` (step-up, below) plus a partial settings object of the same shape, for example `{ "currentPassword": "…", "aiReferences": { "minAssistants": 0 } }`. Unspecified keys are unchanged. A body with no settings key (only `currentPassword`, `{}` or `{ "aiReferences": {} }`) is empty and returns 400. The response is the full effective settings, as GET.
- **Step-up (decided by the hub 2026-10-06; part of the pending ADR 0011 amendment, awaiting the owner's acceptance):** `PATCH` requires `currentPassword`, with the rules of section 1: a wrong or locked-account password is 403 `REAUTH_FAILED`, checked after body validation and before any settings change. The reason is that this route can set `minAssistants` to 0 and switch off the ADR 0005 AI-5 integrity gate. GET needs no step-up. `currentPassword` is validated and discarded: never stored, logged or audited, and never in the audit metadata (a planted-password scan covers the 200 and 403 paths). A rejected step-up writes the section 1 re-auth audit row (required; on main only the lock-triggering failure is audited, see section 1, so a test for it is marked pending until the backend follow-up lands) and no `ORG_SETTINGS_UPDATED` row.
- **Concurrency (compare-and-set through the model API):** Prisma's `update` replaces the whole jsonb value, and Postgres `||` is a shallow merge, so a one-statement merge does not exist (and ADR 0006 section 8.5 forbids raw SQL on `organizations`). The service therefore (1) reads `settings`, (2) deep-merges the patch in code, keeping every stored key (including keys outside the allowlist) and not writing defaults back, (3) writes with `organization.updateMany({ where: { id: ctx.orgId, settings: { equals: previous } }, data: { settings: merged } })`, and (4) on 0 rows re-reads and retries a bounded number of times (for example 3), then returns 409 `SETTINGS_CONFLICT`. The audit row is written in the same transaction as the update. A no-op PATCH (every effective value, as the narrow reader returns it, equals the one sent) returns 200 with the effective settings and writes no audit row.
- **One reader, parsed narrowly:** GET and the publish gate read the stored settings through one reader that parses only the `aiReferences.minAssistants` path (or a non-strict read). Strict parsing is for PATCH bodies only: a strict parse of all stored keys would fail on a future allowed key and silently reset the gate to 2 against the admin's choice.
- **Effect:** the new value is read at publish time. It never changes versions that are already published, and a change does not revalidate drafts.
- **Audit:** `ORG_SETTINGS_UPDATED`, request-driven, with actor, IP, `entity_type` `organization`, `entity_id` the org id, and metadata `{ changes: [{ key, from, to }] }` (the old and new values; they are configuration numbers with no secret). `from` is the effective value as the narrow reader returns it (an out-of-range or wrong-type stored value reads as the default), never the raw stored JSON, and only keys whose effective value actually changes appear in `changes`. The values are configuration with no secret and no personal data, so they fit ADR 0001 C-3's "IDs and action names only" intent. A rejected PATCH (400, 403 or 409) writes no `ORG_SETTINGS_UPDATED` row.
- **Errors:** 401 without a valid token, and for a CANDIDATE token (the staff guard accepts only `kind=access` tokens and rejects every other kind at authentication, before any role check; accepted by the hub); 403 for any role other than SUPER_ADMIN (RECRUITER, AUTHOR, REVIEWER); 403 `REAUTH_FAILED` for a wrong password; 400 as above; 409 `SETTINGS_CONFLICT` after the bounded retries. The default staff throttle applies. No 404: the organisation always exists for a valid token.
- **packages/shared:** the strict `orgSettingsSchema` and its patch variant (for PATCH bodies only, not for reading stored settings) belong in `packages/shared` (database.md names it `OrgSettings`; ADR 0007 section 6 approves it). The hub adds them in a small PR (rule 12); until it lands, Backend A may keep a local zod schema with the same shape and moves to the shared one afterwards.
- **Tests (QA assigns TC IDs):** SUPER_ADMIN reads and changes `minAssistants`; each other role gets 403 and a CANDIDATE token gets 401; a wrong or missing `currentPassword` is 403 `REAUTH_FAILED` or 400 and changes nothing; `currentPassword` appears in no log and no audit metadata (planted-password scan, 200 and 403 paths); an unknown key (also nested), a `null`, an empty patch, a value outside 0..5 and a non-integer get 400; two concurrent PATCHes of different keys both survive (compare-and-set retry); a stored out-of-range value reads as 2 in GET and in the gate; one organisation's change is not visible to another (TC-008 style); the audit row has `changes` and no other fields; the publish gate honours the new value (BE-04c).

## 3. Audit rows written by jobs

ADR 0001 C-3 already says jobs write audit rows with a null actor. Convention for every audit row that is not written inside a request by the acting staff user (validation finish, retention and erasure jobs, reconcilers, webhook deliveries):

- `actor_id` is NULL and `ip` is NULL.
- `metadata` carries `system: true`. When the job finishes work that a named user started, it also carries `initiatedBy` (the user id) and `startedAuditId` (the id of the request-driven row that started it, as a decimal string: the id is a bigint), so the two rows can be linked. The actor is not set to the initiator: an append-only log should attribute to a person only what they did in a request.
- TC-006's "actor, entity, IP" applies to request-driven rows (FR-105: staff reads and changes of candidate data). `audit_logs.ip` is nullable (database.md). Tests assert `ip === null`, `actor_id === null` and `metadata.system === true` for job rows.
- Example: `QUESTION_VALIDATION_FINISHED` has metadata `{ system: true, initiatedBy, startedAuditId, version, outcome, revision }`.

## 4. Problem extension members

Besides `code` (section intro), `409 SESSION_NOT_ACTIVE` carries the extension member `sessionStatus` (the session's status, for example `PAUSED`). It is not named `status` because RFC 7807 reserves that member for the HTTP code. 200 bodies that return the session keep the field name `status` (ADR 0013: the section 4 proctor-key "States" row and the section 5.3 heartbeat table). **(architect detail)** It applies to every 409 `SESSION_NOT_ACTIVE` on a candidate route, including batches and presign, and its value is a `session_status` enum value of the token's own session only. `ProblemDetails` in `problem.filter.ts` gains an optional `sessionStatus` when BE-07 or BE-10 implements it.

## 5. Question variants and AI reference rows (DL-35)

Interim rule, confirmed by the hub on 2026-10-06 (the long-term answer is the owner's, P-21):

- Deleting a draft variant that has AI reference rows is refused with 409 and `code` `VARIANT_HAS_AI_REFERENCES`. The author retires the variant instead (ADR 0005 AI-1 append-only; AI-6: rows go only with their question version). This closes the silent loss of `ai_reference_solutions` rows, and with them the publish gate, that `onDelete: Cascade` on `ai_reference_solutions.variant_id` causes today.
- The check and the delete are race-free against a concurrent AI-reference insert: a plain check-then-delete races such an insert under READ COMMITTED. A row lock on the variant (`SELECT ... FOR UPDATE` through a named, reviewed `runRawSql` call site, ADR 0006 section 8.5; it conflicts with the insert's foreign-key `KEY SHARE` lock) is preferred; Serializable with a bounded retry is the alternative, but PostgreSQL's serializable checks do not clearly cover foreign-key lookups, so it must be proven. A two-transaction test proves it, and also proves that a variant with rows survives a delete attempt.
- Defence in depth (needs the owner's schema approval, an ADR 0008 delta for Database A): change `ai_reference_solutions.variant_id` to `onDelete: NoAction`, not `Restrict`. Postgres does not allow `RESTRICT` to be deferred, so deleting a whole draft question version (which cascades to its variants and their AI rows) could abort depending on the cascade order, which would break AI-6's "deleted with their question version". `NoAction` is checked at the end of the statement: it still refuses a direct variant delete and lets the version delete go through.

## 6. Staff user administration (SUPER_ADMIN; FR-103, FR-101, DL-23)

These routes exist on main (`apps/api/src/users/users.controller.ts`) and had no contract entry; this section records them as built. SUPER_ADMIN only (FR-103), own organisation only (org scope from the token; another organisation's user is a 404, as if absent: TC-008). Step-up rule for the four writes: the caller's own `currentPassword` is required, with the rules of section 1 (same check order, same lockout, same 403 `REAUTH_FAILED` for a wrong or locked password, never stored, logged or audited). It is the FR-102 re-auth decision of the admin 2FA reset applied to these routes: a stolen access token alone cannot create or strip admins or unlock accounts. Extending the step-up beyond the 2FA routes is part of the pending ADR 0011 amendment awaiting the owner's acceptance; it is stricter, so it is already on main ahead of that acceptance.

| Method and path                      | Body                                                | Success                                      | Purpose                                                                                                   |
| ------------------------------------ | --------------------------------------------------- | -------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| `GET /admin/users`                   | query `page`, `pageSize`                            | 200 `StaffUserList`                          | Staff users of the organisation. Audited `USER_LIST`. No step-up.                                         |
| `GET /admin/users/lock-events`       | query `page`, `pageSize`                            | 200 `LockEventList`                          | Recent account lockouts, newest first (FR-101, P-03). Audited `USER_LOCK_EVENTS_LIST`. No step-up.        |

| `POST /admin/users/:userId/invite`   | `{ currentPassword }`                               | 200 `StaffUser`                              | Re-issue the invite of a user who has no password yet: new link, the old one stops working (DL-23). Audited `USER_INVITE_REISSUED`. |

| `POST /admin/users/:userId/unlock`   | `{ currentPassword }`                               | 204                                          | Clear the login lockout (FR-101). Does not change the password or the sessions. Audited `USER_UNLOCKED`.  |

Rules:

- **Check order:** authentication and role guard (a role or permission denial is a plain 403 with no `code`; a non-staff token is 401), then body and path validation (400: a non-UUID `userId`, a missing `currentPassword`, an invalid email, name or role, neither `role` nor `active` on PATCH), then the password (403 `REAUTH_FAILED`), then, for invite and re-issue, the invite limit (429; 503 if Redis is down; a slot is used even when the request later fails with 404 or 409, and is given back on a 503 `BUSY`, section 8), then the by-id lookup (404 for a missing or other-organisation user, only after the password succeeded, so a wrong password gives the same 403 whatever the target), then the state checks (409).
- **`StaffUser`:** `id`, `email`, `name`, `role`, `status` (`invited`, `active` or `deactivated`), `locked`, `lockedUntil`, `totpEnabled`, `createdAt`. `locked` and `lockedUntil` appear on these routes and nowhere else (FU-BE-22); `lockedUntil` is null unless the account is locked now. Paging: `page` at least 1, `pageSize` 1 to 100 (default 50), and `page * pageSize` over 10 000 is 400. A failed invite mail does not change the 201 or 200 response (the user or the rotation stays; only the error name is logged). A PATCH that changes nothing returns 200 and writes no audit row. An admin can unlock their own account, and unlocking an unlocked account succeeds and is audited with `wasLocked: false`.
- **409 conflicts (three reachable):** invite with an email that is already in use (`users.email` is unique across all organisations, so the 409 shows only that the address is in use somewhere: a recorded cross-tenant signal, see the follow-up below; DL-36: the 409 writes a `USER_INVITE_CONFLICT` audit row, written outside the rolled-back create, with actor, organisation, IP and time, `entity_id` null and metadata `{}` (no email and no user id), so a probe leaves a trail; Backend A #174. If the conflict insert fails, the request returns 500, never an unrecorded 409); re-issue for a user who already has a password or is deactivated; PATCH of the caller's own role or status. A fourth check (leaving the organisation without an active SUPER_ADMIN) is a defensive guard that cannot be reached today, because the caller is always another active SUPER_ADMIN; it is not tested.
- **Invite and re-issue:** the response never carries the link. The link is `<web origin>/admin/set-password#token=<32-byte token>`: the token sits in the URL fragment so it is not sent in the page request, the Referer header or any access log (the web app later sends it in the body of the acceptance call, the same hardened route as a password reset: single use, expiry, revokes sessions, never signs in; `token` is on the redact list); it is single use and expires after 72 hours. Re-issue replaces the stored token hash, so the old link stops working. Both routes share a per-organisation limit of `INVITE_RATE_LIMIT_PER_ORG_HOUR` (default 20) invitations per hour: 429 over the limit, and 503 when the limiter (Redis) is unavailable (fail closed).
- **Revocation on PATCH:** a role change or deactivation changes the `users` row first and then revokes the refresh tokens in one transaction; access tokens issued so far stop working through a Redis marker, and a Redis outage rolls the whole change back with a 503.
- **Throttle and audit:** the default staff throttle applies. Every write above is audited, request-driven, with actor and IP; no audit metadata contains a password, a token or a link.
- **Tests (QA assigns TC IDs):** each non-SUPER_ADMIN role gets 403; a wrong or locked password is 403 `REAUTH_FAILED` with the same body for every target (existing or not, own or other organisation); a missing `currentPassword` is 400; other-organisation and unknown users are the same 404; the three reachable 409 cases; the invite limit (429) and the Redis-down 503; a role change or deactivation revokes sessions at once (FR-104); the link is never in a response, a log line or an audit row (planted-token scan).

## 7. Manual scoring of short answers (BE-13; D-23, FR-205, TC-099)

Proposed by Backend B (BE-11 review) and shaped by the hub on 2026-10-06. The FSD section 4 row is the owner's, through the Delivery Lead's batch; the binary score is also flagged to the owner as a design choice.

| Method and path                                                | Who                                          | Body                                            | Success                                     |
| -------------------------------------------------------------- | -------------------------------------------- | ----------------------------------------------- | ------------------------------------------- |
| `PATCH /review/sessions/:sessionId/answers/:sessionQuestionId` | REVIEWER, SUPER_ADMIN (`review_verdict:set`) | `{ correct: boolean, note?: string (1..1000) }` | 200 `{ sessionQuestionId, correct, score }` |

Rules:

- **Check order:** guard (401 for a non-staff token, 403 for another role), then body and path validation (400), then the org-scoped lookup of the session and the question (404), then the answer type and scoring state (409 `ANSWER_NOT_MANUAL`), then the session status (409). The 404 comes before every 409, so a cross-organisation id never reveals a status.
- **Who may score:** any REVIEWER or SUPER_ADMIN of the organisation, the same as the verdict route. There is no claim or assignment model in BE-13 (`session_reviews.reviewer_id` records one reviewer per session); revisit this if a claim or conflict-of-interest rule is added.
- **Permission:** the existing `review_verdict:set`. The reviewer who sets the verdict also scores the answers that block it (TC-099), so no new permission is needed.
- **Org scope and ids:** the organisation comes from the token. `:sessionQuestionId` must belong to `:sessionId`, and the session must be in the caller's organisation. An unknown `sessionId`, another organisation's session, or a `sessionQuestionId` that belongs to a different session are all the same 404 (TC-008).
- **Which answers:** a SHORT_ANSWER question whose `scoring` is `MANUAL_PENDING` (an answer that did not match after normalisation, D-23) or already `MANUAL` (a decision being changed). The first decision sets `scoring = 'MANUAL'`, `score`, `scored_by`, `scored_at` and `scoring_note` (ADR 0007 section 10). Any other question (MCQ, coding, or a short answer scored `AUTO`) is 409 `ANSWER_NOT_MANUAL`. Coding questions that ADR 0016 section 8.1 would put in `MANUAL_PENDING` after repeated Judge0 failures (owner question 10, undecided) are not covered: if the owner accepts that, this route or a sibling must accept CODING, and the reviewer's note would replace the system's "execution failed" `scoring_note`.
- **When:** the session must be UNDER_REVIEW (C-28: `route-session` moves every session there after grading, ADR 0014). Any other status that is not COMPLETED is 409 `SESSION_NOT_UNDER_REVIEW`. A COMPLETED or APPEALED session (a verdict is set) is 409 `VERDICT_ALREADY_SET` and wins over `SESSION_NOT_UNDER_REVIEW`. Until the verdict a reviewer may change a decision (the last one wins; every change is audited).
- **Race-free with the verdict and between scorers:** the scoring and the verdict transactions both take the `sessions` row first. Scoring takes the lock with a status-guarded `sessions.updateMany({ where: { id, status: 'UNDER_REVIEW' }, data: { total_score: null } })` (`sessions` has no `updated_at`, so `total_score` is the lock column; writing NULL is safe because it is overwritten in the same transaction; 0 rows is 409, `VERDICT_ALREADY_SET` or `SESSION_NOT_UNDER_REVIEW` after a re-read). Only then does it read `previousCorrect`, update `session_questions`, and **recompute the total from `session_questions` inside the transaction**, writing it with a second `sessions` update: NULL while any answer is still `MANUAL_PENDING`, otherwise the sum. Under READ COMMITTED every statement after the lock sees the previous lock holder's commit, so two scorers on different answers of one session cannot leave a stale total. A reviewed `runRawSql` `SELECT ... FOR UPDATE` (ADR 0006 section 8.5) is an acceptable alternative lock. The verdict makes its UNDER_REVIEW to COMPLETED compare-and-set first (or a reviewed `FOR UPDATE`), counts pending answers after it, and rolls the whole transaction back if any remain (the status stays UNDER_REVIEW). So no score or total changes after the verdict, and two concurrent scorers record the right `previousCorrect`.
- **Score:** `correct: true` gives the question's full `points`; `correct: false` gives 0. No partial credit. `score` in the response is a number (the column is `numeric(6,2)`, serialised as a JSON number).
- **Effect on the verdict:** `POST /review/sessions/:id/verdict` answers 409 while any answer of the session has `scoring = 'MANUAL_PENDING'` (ADR 0007 section 10; TC-099). `sessions.total_score` stays NULL while any answer is pending, is computed when the last one is decided, and is recomputed on each later change before the verdict.
- **Note:** `note` is stored with the decision (`scoring_note`) and shown in the review bundle; it is staff-written free text and is not copied into the audit metadata. A decision change that omits `note` keeps the previous note; a whitespace-only note is 400.
- **Audit:** `ANSWER_SCORED_MANUALLY`, request-driven, with actor, IP, `entity_type` `session`, `entity_id` the session id, and metadata `{ sessionQuestionId, correct, previousCorrect }` (ids and booleans only; `previousCorrect` is null on the first decision; never the answer text or the note). A staff change to candidate data, so FR-105 applies.
- **Errors:** 400 for a non-UUID id, a missing or non-boolean `correct`, a note outside 1..1000 characters or an unknown key; 401; 403; 404; 409 `ANSWER_NOT_MANUAL`, `SESSION_NOT_UNDER_REVIEW` or `VERDICT_ALREADY_SET`. The default staff throttle applies.
- **Tests (QA assigns TC IDs; TC-099 anchors the main flow):** each non-reviewer role gets 403; cross-organisation and cross-session ids are the same 404; a non-manual question is 409; a decision before UNDER_REVIEW and after the verdict are 409 with `VERDICT_ALREADY_SET` winning on a COMPLETED session; the verdict is blocked until every manual answer is decided and the total score follows each change; a second decision on the same answer succeeds and is audited with the right `previousCorrect`; two-transaction tests of scoring against the verdict, of two concurrent scorers on the same answer, and of two concurrent scorers on different answers of one session (`total_score` equals the sum of the scores); the audit row has ids and booleans and no answer text or note.

## 8. Lock contention (DL-37)

The global `ProblemFilter` (Backend A, `apps/api/src/common/`) maps the database's contention errors on every HTTP route, so no route invents its own answer: PostgreSQL lock timeout (55P03), deadlock (40P01), serialization failure (40001), Prisma P2028 (transaction timeout or closed) and P2034 (write conflict or deadlock) all become **503 with a `Retry-After` header of 1 to 2 seconds and the fixed problem `code` `BUSY`**, never 409 and never 500, except the audit-write carve-out below, the refresh route's unknown-commit 401 (Refresh bullet below) and the unknown-outcome 500 on the 2FA confirm, 2FA disable, recovery-code verify and invite routes (bullet below) (it resolves FU-BE-42). A 409 stays reserved for a state conflict (for example the `accommodations` compare-and-set, or a section already closed). This implements the rule of ADR 0013 5.7 (candidate-side 55P03 and 40P01 answer 503 with `Retry-After`; the SDK resends from its FR-702 buffer) once for all routes.

- **Detection:** under Prisma 7 with `@prisma/adapter-pg` (ADR 0009) the errors may arrive as a `DriverAdapterError` whose `cause` carries the SQLSTATE rather than as a Prisma code, so the filter matches both the Prisma codes and the underlying SQLSTATE (`cause.originalCode` or the equivalent, confirmed by a spike), and no case falls through to 500 (except the post-commit audit write below and the unknown-outcome 500).
- **Pool exhaustion (FU-BE-197, DL-42).** A request that waits longer than `DB_CONNECT_TIMEOUT_MS` (5 seconds by default) for a free database pool connection also answers **503 with `Retry-After` and `code` `BUSY`**, not a generic 500. A pool wait that fails before the route's transaction starts is like any other `BUSY`: the undo rule below applies, so a counter or slot taken earlier (such as the submit counter) is given back, because the action did not take place; pool timeouts carry no SQLSTATE, so the undo catch must match the pool timeout as well as the five contention errors. A pool wait that fails after the action committed (a later transaction, or the post-commit audit write) is not an undo case (the action happened); it follows the rule for a P2028 raised after a commit and, once the audit-write carve-out (PR #230) is merged, that carve-out (the typed error, the fixed 500, or the unchanged response on auth routes); the pool timeout is added to that carve-out's trigger list. The log line names the error and the pool, never the query, and the filter raises the same metric as for P2028 so a sustained shortage is visible. A separate code is not needed: the client action is identical. (As built in #255, to be confirmed.)
- **P2028** also means "transaction already closed or not found", usually a code bug such as using `tx` after commit. It keeps the 503 (on refresh, see its bullet), but the filter logs the error name at error level and raises a metric or alert, so the bug is not hidden.
- **Body and logs:** the body carries no detail from the database; logs record only the error name and SQLSTATE, never Prisma `meta`, query text or parameters.
- **Auth routes:** the mapping must not make an existing account distinguishable from an unknown one. Contention on a login or lockout-counter update answers the same 503 whether or not the account exists, and a login path that touches a per-account row only for existing accounts must not let a caller steer contention onto it. Check this when the filter lands; a difference is a blocker under the auth rule.
- **Refresh (`POST /v1/auth/refresh`):** the rotation (insert of the new token and flip of the old one) is one transaction. (1) A failure before the transaction's callback returns (a lock timeout, deadlock, pool wait, a connection error before or during the callback (FU-BE-209: nothing ran or the server rolls the open transaction back when the connection drops, so it is not a 500; this is decided per route, by the route's callback-returned flag, and is not a global filter mapping: the filter cannot see the flag, and on any other route a connection error stays as it is today unless that route tags it as pre-commit), or a P2028 from the transaction timing out mid-callback) is a rollback: 503 `BUSY`, and the retry with the old cookie is safe. (2) A failure after the callback returned (set a flag at that point) other than 40001, 40P01 or P2034 (those are rollbacks: 503 `BUSY`), including P2028 or P1017 at COMMIT and a driver connection error, has an unknown outcome. The route answers the fixed 401 of a failed refresh with no `code` `BUSY` and no `Retry-After`, **and clears the refresh cookie** (only in this case; never on an ordinary 401, which would wipe a winning tab's new cookie), because a retry or a later silent refresh with the rotated-away token would revoke the family and write a false theft alert (TC-005). The client signs in again. Backend may resolve the unknown by re-reading the old row on a fresh connection with `SELECT ... FOR UPDATE`, so the read waits for any commit still in flight: `revoked_at` null means nothing committed (503 is safe), `replaced_by_id` set means 401. A plain read is not allowed, because it can see null just before the commit lands. (3) **Reuse and other revocation paths** (a rotated token coming back, an inactive user, a role that needs 2FA, a changed password): `revokeFamily` runs outside the transaction. If it fails with any database error, connection errors included (the connection rule of part (1) does not apply to it, because it is a separate statement outside the rotation transaction), it is retried a bounded number of times inside the request. On final failure the route answers the fixed 401, never 503 `BUSY` (an attacker holding a stolen token does not retry, so a 503 would let detected theft fail open), logs at error level and raises the same alert or metric as the audit carve-out. A failed refresh never answers 500 for database or contention errors. Tests (QA assigns TC IDs): a forced commit-time P2028 gives that 401, clears the cookie and leaves the family live; a forced pre-commit lock timeout gives 503 `BUSY` and the old token rotates on the retry; a forced 55P03 on `revokeFamily` during reuse gives 401 and fires the alert. A server-side reuse grace for two tabs was considered and rejected for now (D-66): reuse revokes the family at once, and the two-tab case is handled on the client by a single-flight refresh across tabs.
- **Outcome unknown on a write (FU-BE-208).** Covers exactly five routes: `POST /auth/2fa/setup/confirm` (signed in), `POST /auth/2fa/enroll/confirm` (forced enrolment, challenge token, no session; retired by D-70, so this route drops out of the list when it is removed), `POST /auth/2fa/disable` (FU-BE-219: a landed commit revokes the caller's sessions, so a retry would present a revoked token and the web would refresh and loop), the staff invite and re-issue routes, and `POST /auth/2fa/verify` when the code given was a recovery code (FU-BE-219: the code is spent and a session may exist, so a 503 that releases the challenge invites a retry that cannot work; no secret is learned, because the 500 follows a correct code and cannot be steered by a caller). Recovery-code regeneration is not on the list: a retry after a landed commit only issues a fresh set, so it stays 503 `BUSY`. Refresh is excluded (its own rule above). When the action's own transaction fails after its callback returned (set a flag at that point; P2028 or P1017 at COMMIT, a driver connection error; 40001, 40P01 and P2034 are rollbacks and stay 503 `BUSY`), the commit may or may not have landed. A connection error before the callback returned (FU-BE-209) is a rollback or nothing ran: 503 `BUSY`, never this 500. The route throws a typed error (for example `OutcomeUnknownError`, like `AuditWriteAfterCommitError`) and the filter maps only that type to a **fixed 500 problem document: the generic 500 body, no `code`, no `Retry-After`, no database detail**, the log line and metric naming only the error and the route (same shape as the audit-write carve-out, but defined here, so it stands if that carve-out changes). It is not 503 (an automatic retry would repeat the action), not 409 (a retry's 409 looks like a probe and says nothing about the first attempt) and not 401 (the web would refresh and replay). No new `code` is added: the web recognises the case by route and status, which keeps the `PROBLEM_CODES` lists and the web enum unchanged. **The web never auto-retries it** and shows a fixed message that says the result is unconfirmed. Client step per route: (a) setup/confirm (D-70: a landed commit revokes all of the user's refresh families, so a refresh cannot be used to read the state): call `POST /auth/logout` and go to sign-in. If the commit landed, sign-in asks for the TOTP code and the user then regenerates the recovery codes (`{ currentPassword }`), never re-confirming with the same code; if not, sign-in does not ask and the user restarts setup. (b) enroll/confirm: there is nothing to read, so go to sign-in. If the commit landed, sign-in asks for the TOTP code (the QR code was already scanned), and the user then regenerates recovery codes; if not, sign-in restarts enrolment. (c) invite and re-issue: read the user list; if the user is there, the invite happened. (d) disable: call `POST /auth/logout` and go to sign-in, as after a 204 (without the logout a commit that did not land leaves a valid refresh cookie and the next page load refreshes silently). If the commit landed, sign-in no longer asks for the TOTP code; if it did not, it does, and the user may disable again by hand after signing in. (e) 2FA verify with a recovery code: start sign-in again from the password step (the challenge is not released on this 500); if the recovery code is now rejected it was spent, so use another one or the authenticator code; a session the commit may have opened was never delivered and is unusable (as FU-BE-184). **Counters.** An action slot taken before the transaction (the invite slot) is not refunded on this 500, because the refund of the undo rule is for a 503 `BUSY` only, so a retried invite cannot get a free slot. **The typed error must not be visible to the contention classifier.** If it carries the original P2028 as a `cause` and is a plain `Error`, `lockContentionCode` still finds the code, the challenge is released and the attempt refunded, which breaks both promises of this bullet. Make `OutcomeUnknownError` (and `AuditWriteAfterCommitError`) an `HttpException` 500 subclass, or make the classifier stop at it, and test that the challenge is kept and no refund happens. **A failed-attempt reservation is never given back on this 500 (FU-BE-220).** The refund decrements the shared counter, and after a landed commit the counter was already reset by the success path, so the decrement would erase a concurrent counted guess and give an attacker one extra guess; when the outcome is unknown the cost of keeping it is one attempt for a legitimate user. The fail-safe direction is to keep the count. A give-back that already happens before the transaction (disable gives back its code reservation once both factors have passed) is unaffected, and Backend does not move it. On a definite-rollback 503 of disable, the access-token marker set inside the callback may already have ended the caller's access tokens; the client's retry then refreshes once and succeeds, which fails safe and is an accepted exception to the undo rule's "no external call was made". Backend may use the locking re-read of the refresh bullet (`FOR UPDATE` on the target row) to turn an unknown outcome into a definite success or 503 `BUSY`. The rule changes no token, secret or guess handling and adds no oracle (the answer depends on the failure, reached only after the password or challenge and the code verified), so it is technical contract text. Tests (QA assigns TC IDs): a forced commit-time P2028 on each of the five routes gives that 500 with no `Retry-After` and no `code`; the invite slot is not given back; a forced pre-commit lock timeout still gives 503 `BUSY` and the slot is given back.
- **Undo before the 503 (side effects).** A 503 invites a retry, so a route that has a counter or slot taken before its database transaction undoes it before the error propagates, but only when the action did not take place: the transaction did not commit and no external call was made. Example: the submit counter `INCR submits:{sid}:{sqid}` (ADR 0013 5.11). The undo is a catch that decrements and rethrows, or a `finally` guarded by a not-committed flag; an unconditional decrement in a `finally` would also undo successful submits and is wrong. A P2028 raised after a commit is not an undo case, because the action happened. **Never refunded on a 503:** a Run that reached Judge0 keeps its slot (FR-502, ADR 0016 section 10; any give-back is owner question 9), and the global throttle, the login throttles and the lockout and failed-attempt counters are never refunded, because refunding them would let a caller who can cause contention get uncounted guesses. One exception (FU-BE-192): a failed-attempt reservation whose secret has already verified (a correct password or a correct code) is given back when a later step fails with a 503 `BUSY` that is a definite rollback, and never after a commit that landed or may have landed (the unknown-outcome bullet, FU-BE-220), because the caller learned nothing and gets no extra guess; a wrong password or a wrong code is never refunded. The staff invite slot of section 6 is given back on a 503 `BUSY`, since no invite was created; the 503 for Redis being down carries no `BUSY` code. Backend owns each route's undo.
- **Carve-out: an audit write that fails after the handler committed (proposed, owner to approve).** Where a route writes its audit row in a separate transaction after the action's own transaction has committed (some routes already write it inside the action's transaction and are not affected), and that audit write fails, including by lock contention (55P03, 40P01, 40001, P2028, P2034), the route answers a **fixed 500 with no `Retry-After` and no `code` `BUSY`**, because the action already took effect and a 503 would invite a retry of a non-idempotent staff action (an invitation, an admin 2FA reset), which would run twice. The body is the generic 500 problem document with no detail from the database. The audit service wraps a post-commit failure in a typed error (for example `AuditWriteAfterCommitError`, carrying the cause and the action name), and the filter maps only that type to the fixed 500; SQLSTATE alone cannot tell a post-commit audit write from the action's own transaction, so every other contention error stays 503 `BUSY`. Web and SDK clients must not auto-retry a 500 on a staff write. The filter logs the error name and the audit action at error level and raises a metric or alert, so a missing audit row (FR-105) is never silent; it logs no request data, and the metric or alert is labelled with the audit action only, never an `entity_id`, actor or organisation id. **Auth routes** (login, the lockout and failed-attempt paths such as `recordLock`, the re-auth failure audit, refresh reuse): a failed post-commit audit write does not change the response. The route answers exactly what it would have answered without the failure, and the failure is logged and alerted as above, so an existing account is never distinguishable from an unknown one (the auth-route rule above); the alternative is to write the audit row in the counter's own transaction. The carve-out applies only to the post-commit audit write. One exception: the notification audit row of the 2FA email (section 1, D-76) is exempt on its four routes; its failure never changes the response and is logged and counted as described there. Contention in the action's own transaction stays 503 `BUSY`, because nothing committed. The root gap is that the audit row is outside the action's transaction; the architecture follow-up to move it inside removes the reason for this carve-out, and the carve-out is then deleted.
- **Jobs** keep their own handling: `SessionJobProcessor` (`busy-lock.ts`, Backend B) maps the same errors to a BullMQ retry.
- **Tests (QA assigns TC IDs):** (except the refresh route, see its bullet) each of the five errors, delivered both as a Prisma code and as a driver SQLSTATE, on a staff route and a candidate route gives 503 with `Retry-After` and `code` `BUSY`; none gives 409 or 500 (except the post-commit audit write and the unknown-outcome 500 of its bullet); a forced audit failure after commit gives a fixed 500 with no `Retry-After` and no `code`, the action is neither reversed nor repeated, the alert or metric fires and the log line has no request data; a forced audit failure on the lock-triggering login of an existing account gives the same response as an unknown account; contention in the action's own transaction still gives 503 `BUSY`; under induced contention a submit returns 503 `BUSY` with the counter unchanged, a successful submit keeps its increment, and a Run that reached Judge0 keeps its slot; the body never contains SQL, table or column names; a login for an existing and an unknown account under induced contention answers the same. Under pool exhaustion a submit returns 503 `BUSY` with the counter unchanged, and a post-commit audit write that hits pool exhaustion does not return `BUSY`.
