# API contract (ARC-02)

Authoritative REST contract (ADR 0001 C-8). BE-01 exists, so a route moves to the code-first OpenAPI once the backend publishes it there and ARC-02 part 2 confirms it matches; until then this file wins. Paths follow the backend's routes under `/api/v1`; ARC-02 part 2 settles the remaining paths, adds the other endpoint groups and the fsd.md §4 rows.

Errors are RFC 7807 problem details (ADR 0001 C-9, as implemented in `problem.filter.ts`: `type`, `title`, `status`, `detail`, `instance`, `traceId`, `errors`). This contract adds one extension member, **`code`** (a stable machine-readable string such as `REAUTH_FAILED`). `ProblemDetails` in `apps/api/src/common/problem.filter.ts` carries an optional `code` (already on main). `code` is set only where this contract names one: `REAUTH_FAILED` and `TWO_FACTOR_REQUIRED_FOR_ROLE` (the `PROBLEM_CODES` in backend PR #26). Guard 403s (role or permission denial) carry no `code`. Clients branch on `code`, never on `detail` text.

## 1. Re-authentication for 2FA management

Owner decisions (C-21, 2026-10-05, D-49; ADR 0011, Accepted): `currentPassword` is required on 2FA setup, disable and recovery-code regeneration; a wrong password returns 403 `REAUTH_FAILED`; forced enrolment is unchanged; the six answers are recorded below. Rules marked **(architect detail)** were added by the architecture hub to make the decision implementable and are covered by C-21's acceptance of ADR 0011.

### Endpoints

| Method and path                                         | Who                                                  | Body                                     | Success                                                            |
| ------------------------------------------------------- | ---------------------------------------------------- | ---------------------------------------- | ------------------------------------------------------------------ |
| `POST /auth/2fa/setup/start`                            | Any staff, signed in                                 | `{ currentPassword }`                    | 200, otpauth URI, manual key and `qrDataUrl`                                    |
| `POST /auth/2fa/setup/confirm`                          | Any staff, signed in                                 | `{ currentPassword, code }`              | 200, the 10 recovery codes, shown once                             |
| `POST /auth/2fa/disable` | Any signed-in staff; refused for roles whose 2FA is mandatory (SUPER_ADMIN, REVIEWER): 403 `TWO_FACTOR_REQUIRED_FOR_ROLE` (C-21) | `{ currentPassword, totpCode }` (`totpCode`: a current 6-digit TOTP code, never a recovery code (**architect detail**: stricter than C-21's "a current 2FA code"; a user who lost their device turns 2FA off through an admin reset); **backend PR #51, pending merge**; until it lands send only `currentPassword`: main runs with `forbidNonWhitelisted`, so an unknown `totpCode` field is a 400) | 204. **After #51 (pending):** revokes all of the user's refresh sessions, the caller's included, and clears the refresh cookie. **On main:** revokes nothing and leaves the cookie. Either way the UI calls `POST /auth/logout`, then goes to sign-in |
| `POST /auth/2fa/recovery-codes/regenerate`              | Staff with 2FA on (409 if off) **(architect detail)** | `{ currentPassword }`                    | 200, 10 new codes; the old ones stop working                       |
| `POST /auth/2fa/reset/:userId` (C-21)                    | SUPER_ADMIN, same organisation; not for the caller's own account (400, checked before the password) | `{ currentPassword }` (the admin's own)  | 204; an unknown or other-organisation `userId` is 404 (ADR 0006); revokes the target's refresh sessions |

The paths are the routes on main (backend #26); ARC-02 part 2 pins them in fsd.md §4.

### Rules

- `currentPassword`: a string of 1 to `MAX_PASSWORD_LENGTH` characters, the same bound as login; never trimmed or normalised **(architect detail)**.
- **Wrong password: HTTP 403, problem `code: "REAUTH_FAILED"`**, `detail` "The current password is incorrect.". It is not 401: the session is valid, and a 401 means "access token expired" to the client (it would refresh and retry).
- **Locked account (architect detail).** While `locked_until` is in the future, the check burns an Argon2 verify and returns the identical 403 `REAUTH_FAILED` even for the correct password, so a locked account gives no signal and the route cannot be used to keep guessing. Wrong attempts count towards the same lockout as login (FR-101, TC-002); the failure that triggers the lock writes the same account-locked audit row as login. On main a successful re-auth does not reset the failed-login counter; it only gives back its own attempt reservation (BE-02 may confirm or change this).
- Check order (as implemented in #26): authentication and role guard (a role or permission denial is a plain 403 with no `code`), then body validation and path validation (400, including a UUID check and, for reset, a self-target which is 400), then the password (403 `REAUTH_FAILED` when wrong or locked), then the remaining checks; **for `disable` as implemented in #51**: password, then 409 if 2FA is off, then the TOTP code (wrong or replayed code: 403 `REAUTH_FAILED`, same body as a wrong password, counted toward the same lockout), then the role refusal (deliberate in #51: the role refusal comes last, so a SUPER_ADMIN or REVIEWER must give a valid code before hearing "required for your role"; on main it comes right after the password). A missing or malformed `totpCode`, or a recovery code in its place, is a 400 from body validation, before the password check; **for `disable` as in #26 (until #51 merges)**: a role whose 2FA is mandatory gets 403 `TWO_FACTOR_REQUIRED_FOR_ROLE` (after the password, so it is not revealed without it); the 409 when regenerate or disable is called with 2FA off is also after the password and is not a guard; an unknown or other-organisation reset target is 404. A wrong TOTP `code` on setup/confirm after a correct password is the ordinary 2FA validation error (400 "That code is not valid."), not `REAUTH_FAILED`; on main it also counts toward the lockout, and a locked account there gets the same 400 as a wrong code (the Security page error copy must not assume the cause).
- Every re-auth success and failure is audited: who, which action, outcome, never the password **(architect detail; required, not fully on main: today only the completed actions are audited (`AUTH_TOTP_ENABLED`, `AUTH_2FA_DISABLED`, `AUTH_RECOVERY_CODES_REGENERATED`, `AUTH_2FA_RESET_BY_ADMIN`) and the failure that triggers the lock; a failed re-auth otherwise and a successful `setup/start` write no audit row: backend follow-up)**.
- `currentPassword`, `password` and `newPassword` must be on the API's pino redact list as defence in depth (`req.body.currentPassword`, `req.body.password`, `req.body.newPassword`, and the same under any logged error context), and validation errors must never echo submitted values.
- **Forced enrolment is unchanged.** Roles whose TOTP is mandatory (FR-102) enrol during login through the challenge-token flow (`/auth/2fa/enroll/start` and `/confirm` with `challengeToken`), which already follows a password check. It takes no `currentPassword` and issues no access token until enrolment is confirmed (TC-003).

### Owner answers (C-21, 2026-10-05, D-49)

1. A SUPER_ADMIN reset needs the admin's own password. Matches #26.
2. Re-auth failures share the login lockout (five wrong attempts lock login for 15 minutes). Trade-off noted: someone holding a stolen access token can lock the real user out repeatedly; an anonymous attacker who knows the email can already do that, so there is no new exposure. Matches #26.
3. Mandatory-2FA roles (SUPER_ADMIN, REVIEWER) cannot disable 2FA: 403 `TWO_FACTOR_REQUIRED_FOR_ROLE`, checked after the password. Matches #26.
4. An admin can reset another admin's 2FA but not their own: a self-reset is 400, checked before the password. Matches #26.
5. Disabling or resetting 2FA revokes that user's sessions. Reset already revokes the target's refresh-token families in #26; disable revokes them too (backend PR #51, pending merge; until then a disable does not revoke). Access tokens already issued expire within 15 minutes, so this is not an immediate compromise response.
6. Disabling 2FA also needs a current TOTP code. `totpCode` is required in `{ currentPassword, totpCode }` (backend PR #51, pending merge; #26 requires only the password today).

### Frontend (Security page)

- After a successful `disable` (204), always call `POST /auth/logout` and then go to sign-in. **On main (before #51 merges)** disable revokes nothing and leaves the `cp_refresh` cookie valid, so clearing client memory alone would let the next page load refresh silently; the logout call revokes the caller's family and clears the cookie, and is harmless after #51 (which signs the user out everywhere itself). Access tokens already issued live up to 15 minutes (FU-BE-59).
- Setup: one password prompt that keeps the password in component state from `start` through `confirm`; clear it on confirm, error or close. Disable and regenerate: a prompt per action.
- On 403 with `code: "REAUTH_FAILED"` show "Password is incorrect" inline (for `disable` after #51 show "Password or code is incorrect": the body deliberately does not say which) and keep the dialog open; do not sign out and do not refresh. `TWO_FACTOR_REQUIRED_FOR_ROLE` means this role must keep 2FA (hide or disable the control for SUPER_ADMIN and REVIEWER); any other 403 is a permission problem, not a password problem.
- The bearer-authenticated routes (`/auth/2fa/setup/*`, `disable`, `recovery-codes/regenerate`, `reset`) must not count as auth requests in `isAuthRequest`, so that a real 401 (expired access token while the dialog is open) refreshes and retries once. The challenge-token routes (`/auth/2fa/enroll/*`, `/auth/2fa/verify`), login, refresh and logout stay excluded. The retry copy of the request (it carries `currentPassword`) must be dropped when the retry settles; the password stays in memory only, never in storage. Today every `/v1/auth/*` path is excluded from refresh.

### Session user: `totpEnabled` (Delivery Lead decision, hub conditions)

**Not on main yet: backend follow-up (owner: backend-engineer, task to be assigned by the Delivery Lead), pending.** `AuthUserDto` today is `{ id, email, name, role, orgName }` (`apps/api/src/auth/dto/auth.dto.ts`). It will gain `totpEnabled: boolean`, returned wherever an authenticated session user is returned (a completed login, `2fa/verify`, enrol confirm, `refresh`). There is no `GET /auth/2fa/status` route. Until the backend change lands the field is `undefined`: Frontend must treat `undefined` as unknown, must not render an "Enable 2FA" call to action from it, and shows the Security page without the on/off state (setup/start answers 409 when 2FA is already on). The web reads the flag from the session user and, after setup/confirm (which returns no session user), sets it to `true` locally on the 200 and confirms it on the next `/auth/refresh`; disable signs the user out, so no re-read is needed there. Conditions: it appears only in responses that already carry an authenticated session user, never in the pre-2FA login responses (`two_factor_required`, enrolment required) or any unauthenticated response; it describes the caller's own account only; it is output only (never accepted in a request body); it is never put into access-token claims, so a stale JWT cannot carry it; a stale value never grants anything because the server checks the real state on every re-auth route. `packages/shared` has no session-user schema today (no `orgName` there either); if one is added it carries the same field (a shared-contract change through the hub).

### Tests (QA assigns new TC IDs for re-auth; TC-002 and TC-003 are cited only for the lockout and forced-enrolment regressions)

FR-102, FR-101, TC-002, TC-003: wrong password is 403 `REAUTH_FAILED` on each endpoint; correct password succeeds; repeated wrong passwords lock; a locked account with the correct password still gets 403 `REAUTH_FAILED`; forced enrolment at login needs no `currentPassword`; a role denial carries no `code`; disable by SUPER_ADMIN or REVIEWER is 403 `TWO_FACTOR_REQUIRED_FOR_ROLE` after the password; a self-reset is 400 before the password; reset revokes the target's refresh sessions; disable without a current TOTP code is refused once the backend follow-up lands; the password never appears in logs or audit records.
