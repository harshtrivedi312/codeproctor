## 1. Goal

Create the two migrations that turn `prisma/schema.prisma` into the reference DDL in /docs/database.md.

- `init`: what Prisma generates, plus the SQL Prisma cannot express.
- `audit_append_only`: creates `app_user` if it does not exist, then grants and revokes.

Also:

- set the local `app_user` password through a localhost-only script;
- point `DATABASE_URL` at `app_user`.

Prove all of it on the existing local volume and on a throwaway database, without any destructive command outside localhost. No agent runs `pnpm db:reset`.

## 5. Step-by-step deliverables

1. **Create `init` without applying it.**
   - Run `pnpm db:migrate --create-only --name init`. The localhost guard runs first.
   - Prisma 7's `migrate dev` no longer runs generate or seed. Run `pnpm db:generate` yourself if the schema changed.
2. **Edit `init`.** Add everything from the DB-02 TODO list and ADR 0008 section 8:
   - `CREATE EXTENSION IF NOT EXISTS pgcrypto;` and `CREATE EXTENSION IF NOT EXISTS citext;` as the first statements;
   - the 12 CHECK constraints (ADR 0008 section 5);
   - the partial indexes on `sessions (risk_band) WHERE status IN ('GRADED','UNDER_REVIEW')` and `sessions (retention_anchor_at) WHERE retention_anchor_at IS NOT NULL`;
   - `GENERATED ALWAYS AS IDENTITY` on the 5 bigint identity columns;
   - the `users.updated_at` trigger;
   - `fk_current_consent_text`, if Prisma did not emit it.
   - Also check the `pause_reason[]` and `bytea` columns.
   - Then compare the file with database.md, statement by statement.
3. **Create `audit_append_only`.**
   - Run `pnpm db:migrate --create-only --name audit_append_only`. It starts empty, because the schema has not changed.
   - Paste the SQL from ADR 0006 section 7.2 exactly: the idempotent role block, schema USAGE, the table and sequence grants, default privileges without `FOR ROLE`, the `audit_logs` REVOKE, and the `_prisma_migrations` REVOKE.
4. **Local password script, `infra/scripts/set-app-user-password.mjs`** (ADR 0006 section 7.4).
   - It runs the localhost guard first and refuses on any problem: `findProblems` from `infra/scripts/local-db-guard.mjs`, or `node infra/scripts/assert-local-db.mjs`.
   - It reads `APP_USER_PASSWORD` from the shell or `.env`, in the same order as `prisma.config.ts`.
   - It connects as the owner role with `MIGRATION_DATABASE_URL`, using the `pg` client, not psql. The workspace must be able to resolve `pg` from `infra/scripts`.
   - It runs `ALTER ROLE app_user WITH PASSWORD …`, with the value quoted by `client.escapeLiteral`. The value never appears on a command line.
   - It prints only `app_user password set`. It is idempotent.
5. **Wire the scripts.**
   - `db:migrate` becomes `sh infra/scripts/db-migrate`. The wrapper:
     1. refuses a `--config` or `--url` argument, in either the `--flag value` or the `--flag=value` form, before anything else. Prisma 7.10.0 `migrate dev` accepts both flags (ADR 0009 section 5, P17), and either could point Prisma at a config or URL the guard never checked;
     2. runs the guard (`node infra/scripts/assert-local-db.mjs`);
     3. runs `pnpm exec prisma migrate dev "$@"`;
     4. runs the password script, unless `--create-only` was passed.
   - In `infra/scripts/db-reset`, uncomment step 4. Change nothing else in that file.
   - Tests (`pnpm test`; stand-in `docker` and `pnpm`, explicit environment, nothing reaches Prisma):
     - `db-migrate` refuses each form of `--config` and `--url`;
     - it refuses a non-local URL before calling `pnpm`;
     - with `--create-only` it does not run the password script;
     - `set-app-user-password.mjs` refuses a non-local URL before connecting, and never prints the password.
6. **`.env.example`.**
   - `DATABASE_URL=postgresql://app_user:change-me@127.0.0.1:5432/codeproctor`. Use `127.0.0.1`, not `localhost` (ADR 0009 section 4.4, accepted risks).
   - The `APP_USER_PASSWORD` comment says: local only, set by `infra/scripts/set-app-user-password.mjs` after migrations (ADR 0006 section 7.4). Staging, pilot and production set it at provisioning from the vault.
   - The local value must match the password in `DATABASE_URL`.
7. **Apply on the existing local volume.**
   - Run `pnpm db:migrate`. Both migrations apply and the password is set.
   - If Prisma reports drift and asks for a reset: stop. Ask the human to run `pnpm db:reset` in their own terminal, then continue. Do not work around it.
8. **Run the checks** in section 7 and paste the commands and outputs into the PR. Never paste a URL that contains a password.

## 7. Acceptance criteria (definition of done)

**Existing local volume (agent):**

- `pnpm db:migrate` applies `init` and `audit_append_only`.
- `pnpm prisma migrate status` reports both applied.
- A second `pnpm db:migrate` changes nothing ("Already in sync").

**Fresh database, without touching the dev volume (agent):**

- Start `postgres:16` with `--rm` on `127.0.0.1:<spare port>`.
- Run `pnpm prisma migrate deploy` with `MIGRATION_DATABASE_URL` pointing at it. Both migrations apply.
- Create a second database in the same container and deploy again. It succeeds: the role block skips because `app_user` already exists.
- Stop the container.

**Grants (agent), connected as `app_user` with `DATABASE_URL`:**

- `SELECT … FROM audit_logs` works.
- `UPDATE audit_logs …`, `DELETE FROM audit_logs` and `TRUNCATE audit_logs` fail with permission denied.
- `SELECT … FROM _prisma_migrations` fails.
- `CREATE TABLE t ()` fails.
- `\du app_user` shows no Superuser, Create role, Create DB, Replication or Bypass RLS.

**Schema (agent):** catalog queries confirm the ADR 0008 section 1 counts: 31 tables, 20 enums, 12 CHECKs, 2 partial indexes, 5 identity columns and 1 trigger. Record them in the PR.

**No secrets:** `git grep -n -i -E "password\s+'" prisma/migrations` finds nothing. The password script prints no secret.

**Guards (agent), by `pnpm test` only (SF2):**

- The DB-01 tests still pass.
- The new tests from step 5 pass.
- The agent never runs `pnpm db:reset` or `pnpm dev:infra:reset`.

**Human-only (the owner, in their own terminal):** with `pnpm dev:infra` running, so that the Compose-port check passes, `pnpm db:reset` drops and re-applies both migrations on the local volume, sets the password again, and the grant checks still pass. The owner records the result in the PR. Without it the PR is not done; the agent never runs this step.

**CI:** CI is green, including the ADR 0009 check that the consent variable appears nowhere it should not.

**Reporting:** report back for architect review, then code-reviewer. You do not merge.
