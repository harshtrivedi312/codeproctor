# Demo smoke checklist (D-67)

Owner: QA A. Created 2026-10-07 for the demo sprint (Delivery Lead request). The goal is one full
local end-to-end run: **invite, consent, identity, test with runs, recording and events, submit,
reviewer sees it.** This is a smoke check, not a test plan: one candidate, one happy path, plus the
few negative checks that cost almost nothing. The full cases stay in `docs/test-cases.md`; the TC
ids below say which one a step touches.

Status of this file: written before the pieces exist. Nothing has been run. The run waits for the
Delivery Lead to say the pieces are on `main`. Where a step depends on something not built yet, the
result is recorded as **Not built** (not Fail) and the owner is named.

## Rules for the run

- Local stack only, synthetic data only: a made-up candidate name, an address on a reserved domain such as `example.test`, generated media, no real face, no real ID. No pilot, staging or production URL, credential, key or bucket (ADR 0009); that includes the staging R2 keys.
- QA does not start or stop the Docker stack (CLAUDE.md rule 14: Database B does), does not run the web dev server (rule 15: Frontend does) and does not start a local Judge0. QA only connects to what is running.
- Local runs of automated checks: at most 2 workers, only suites that were touched (DL-45). The walk below is by hand in the browser.
- Never paste a token, OTP, invitation link, session key or media key into a report, a PR or chat. Write "OTP read from the sink" and the result. Nobody adds a hook or a log line that prints a token or an OTP: reading them needs a mail sink (P-3) or a hook the owner approved after a security review.
- Result per step: **Pass**, **Fail** (what happened, which owner), **Not built** (the missing piece), or **Blocked** (an earlier step failed).

## The walk

One candidate, in order. Steps use the staff UI for the recruiter and reviewer parts and the
candidate pages for the rest. "API check" is the fallback when a UI is not built: use only the
documented routes (docs/api-contract.md). The invitation window comes from the **slot** the
recruiter picks (FR-303, FR-306): the gate opens 30 minutes before the slot start, the timed test
can start only from the slot start, and the invitation expires 15 minutes after the slot start
(ADR 0002). Plan the timing so that the gate steps (D-03 to D-05) are done and Start is pressed
inside that span.

## What counts as the demo being ready

All of D-01 to D-12 Pass, with D-13 allowed to be Not built, and D-05's identity step allowed to be Not built only if the Delivery Lead agrees that a waived or missing identity step still counts as ready. A single Fail in D-02 to D-09 means the
candidate cannot get through, so the demo cannot show a full run. A Fail or Not built at D-08
(events, recording) or D-11 (timeline, replay) means the demo has no proof of the proctoring half:
report it as the most important gap.

## Report format (to the Delivery Lead, one message)

One line per step: `D-nn Pass | Fail <what, owner> | Not built <missing piece, owner> | Blocked`,
then up to five lines of anything else that surprised the walk (slow steps, confusing messages,
anything that looked unsafe). No tokens, OTPs, links, keys or personal data in the message.

## Automated pass (optional, same rules)

When the pieces are on `main`, existing suites cover the same ground without a browser; run only
those that were touched, with at most 2 workers:

- Candidate session routes: `apps/api/src/candidate/candidate-session.e2e-spec.ts` and `candidate-routes.spec.ts`.
- Reviewer access and audit (D-10, D-12): the `tc-004-rbac` and `tc-006-audit` integration suites under `apps/api/test/integration/`.
- The session seeder (`packages/qa/k6/seed/seed.mjs`, not k6) can create sessions up to the consent step against the running API: it needs `SEED_MAIL_URL` for a Mailpit-compatible sink (so it is **Blocked** under P-3 while mail is noop) and the staff password in the environment only, never typed into a shared shell or a report. Its README calls it staging-only; for this run use the local API and a local sink, and `--stop-at CONSENTED`. `SEED_ORG_NAME` must contain "synthetic" and the local host must be in `ALLOWED_HOSTS`, or the run fails on configuration.
