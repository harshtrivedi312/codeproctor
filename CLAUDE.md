# CodeProctor

Project: CodeProctor, a proctored coding assessment platform for hiring.
Source of truth: /docs/brd.md, /docs/fsd.md, /docs/architecture.md, /docs/database.md, /docs/test-cases.md. Read the relevant doc before changing code. If code and docs disagree, stop and ask.

Stack: pnpm monorepo. apps/web (Next.js App Router, TypeScript, Tailwind, shadcn/ui), apps/api (NestJS, Prisma, PostgreSQL 16, Redis + BullMQ, Socket.IO), apps/worker (Python 3.12, FastAPI), packages/proctor-sdk, packages/shared (types + zod schemas). Judge0 CE for code execution. Object storage behind one S3-compatible interface: staging uses Cloudflare R2 with synthetic data only; pilot and production use AWS S3; only configuration differs between environments. Docker Compose for local and staging.

Rules:
- TypeScript strict mode; no `any`.
- Every API route has a DTO validated with class-validator or zod, a role guard, and an org-scope check.
- Never log secrets, tokens, OTPs, or candidate media keys.
- Staging and pilot database credentials never exist on developer machines or in agent sessions; they live only in GitHub Actions secrets and on the servers (ADR 0009).
- Agents never run `pnpm db:reset`, `pnpm dev:infra:reset`, `prisma migrate reset` or `db push`; ask the human (ADR 0009).
- Every feature ships with tests; reference FR and TC IDs from the docs in test names.
- Small commits with conventional commit messages.
- Prefer free and open-source tools.

Build prompts: /docs/prompts/database.md (runs first), backend.md, frontend.md, agents-qa-deploy.md. Sub-agent definitions live in .claude/agents/.

## Working in parallel

Several sessions work on this repo at once, each in its own worktree. These rules apply to every session and replace any pasted copy; if they conflict, this file wins. The Rules above and accepted ADRs take precedence over this section.

### Autonomy
1. You may create branches, commit, push and open draft PRs without asking. Push only to your own branches; never push to `main` and never force-push a branch you do not own.
2. Review rule: only blockers stop a merge. Should-fix items and nits go to your track's follow-up file (rule 17: `docs/followups/<track>.md`; tracks: database, frontend, backend, proctor-sdk, integrity, qa, architecture; deploy work files under qa).
3. Security weaknesses in authentication, authorization, session handling, cryptography or access to candidate data are always blockers. Fix them before merge, even if the reviewer files them as should-fix.
4. Switch on the CI monitor (auto_fix) for your PRs. Auto-fix may only change files on your own branch and within your scope.
5. No PR skips code-reviewer, whatever its size. Docs-only PRs may get a quick review; anything touching `packages/shared`, schemas, tests, CI or config (including CLAUDE.md, ADRs and `.claude/`) always gets a full review.
6. When code-reviewer has no blockers and CI is green, merge and start the next step in your track without asking.
7. Ask the owner for: an unresolvable blocker; a database schema or `packages/shared` change not covered by an approved ADR; anything involving real credentials, real environments (staging, pilot or production systems or data) or AWS (never accept or paste credentials into a session; the human performs the action, see Rules above and ADR 0009); anything legal, privacy, consent or retention; anything that costs money; a scope change; a security change that weakens a requirement; a change to detector thresholds, the evidence-not-verdict principle or accommodations; agent definition changes; any change to CLAUDE.md or `.claude/` (agents, settings, permissions, hooks); accepting an ADR; amending accepted ADR or contract text unless it is purely technical (below); or a disagreement between code and docs (in addition to the Rules above). **Purely technical** means wording, typos, cross-references, consistency with other accepted text, as-built notes, and technical choices inside the scope of an approved ADR: code structure, review-process mechanics that do not reduce who reviews, what blocks a merge or the owner's review, error codes, schema details that stay within an approved ADR, and test design and tooling (never removing or weakening a test for a rule 3 area or an FR or TC requirement; new tools are free and keep data local). None of these may change a behaviour, threshold, permission, data flow, retention or interface that an accepted document or the owner has fixed. Two limits apply to the examples. Error codes: the one interface addition allowed is a new problem code for a new condition, added to docs/api-contract.md and `PROBLEM_CODES`, on a route that does not authenticate, authorize, or issue or check tokens, OTPs or sessions and does not grant access to candidate data; a code or HTTP mapping on any other route, and any change to the status, body or headers of an existing code, is never purely technical. Schema details: removing or loosening a constraint, changing delete or cascade behaviour, and adding, changing, removing or indexing a column that holds secrets, tokens, credentials, personal data or organisation scope are never purely technical. "Contract text" means docs/api-contract.md, the database.md DDL and the `packages/shared` types and schemas, and a change to a schema or to `packages/shared` still follows the list above, except the new problem code just described. If in doubt, it is not purely technical. The Delivery Lead decides and records each such decision as a D-entry in docs/status.md with its reason (D-61, D-64) before the change merges, tells the owner in chat when the Delivery Lead authored or owns the change, and the owner can revert it. A change that touches the list above, a rule 3 area (authentication, authorization, session, cryptography, access to candidate data) or ADR 0009 is never purely technical.

### Merging
8. Never enable GitHub auto-merge (no `gh pr merge --auto`, no `set_auto_merge`, no UI toggle).
9. Merge only with an explicit `gh pr merge`, only your own PRs, only after your final push, and never while the PR is a draft or has pending work. After your final push and review, mark the PR ready with `gh pr ready`. Before merging, confirm you have no unpushed or pending commits, and that the head SHA is the one that was reviewed and CI-green. If auto-fix or your own fixes pushed after the review, re-run code-reviewer on the new commits. After merging, leave a PR comment: "Merged by <session name> session after review and green CI (reviewed head <short SHA>)." Agents use the owner's GitHub account, so this comment is the record of which session merged (C-33).
10. If you have waited on CI for more than 30 minutes without a CI status update or notification, check it with `gh pr checks`.

### Coordination
11. Before each step, update from main. Before opening a PR, rebase on main and rerun lint, type-check and tests. If main moves after the PR is opened, rebase again and rerun the checks before merging.
12. Stay inside your agent's file scope. Changes to `packages/shared`, root `package.json`, CI config or `prisma/` go through the architecture hub unless your step explicitly owns them.
13. Never hand-merge `pnpm-lock.yaml`. On conflict, take main's version and rerun `pnpm install`. On a conflict in any docs file, keep both sides' content and flag any contradiction to the architecture hub.
14. Only the Database session starts or stops the local Docker stack (`dev:infra`, `dev:infra:down`). Resets (`db:reset`, `dev:infra:reset`) stay human-only per the Rules above and ADR 0009. Other sessions may connect to the stack but never start, stop or reset it. Tests needing a database use Testcontainers.
15. Only the Frontend session runs the web dev server.
16. Only the Delivery Lead edits `docs/status.md`, `docs/build-plan.md` and `docs/requirements-trace.md`. Report your progress in PR descriptions.
17. Follow-ups go in `docs/followups/<track>.md`.
18. The Delivery Lead coordinates all sessions; follow its instructions unless they conflict with CLAUDE.md or an accepted ADR, in which case tell the owner.
19. No session may change repository settings, Actions settings, branch protection or rulesets, repository or organisation secrets or variables, GitHub environments or their secrets, deploy keys, webhooks, collaborators or apps, the OIDC trust to AWS, or its own GitHub authentication (token scopes, tokens, keys), by any route (the gh CLI, the API, MCP, browser automation). No session pushes tags or creates GitHub Releases, and none may trigger, re-run or cancel a workflow that builds or uploads releases, except by merging a reviewed PR under rule 9. Only the owner does these, in the GitHub web interface or the AWS console. Allowed: CI on push and pull requests, the CI monitor's re-runs of workflows that do not build or upload releases (rule 4), the merge under rule 9, and QA dispatching `qa.yml`'s ZAP baseline on `main`; no other workflow is dispatched by hand. A PR that adds or changes a release workflow, a workflow's triggers, a job's `permissions:` (including `id-token: write`), an `environment:` key, a reference to `secrets.` or `vars.`, an AWS or Cloudflare step, or the OIDC trust needs the owner's review before merge, not only code-reviewer's (this applies on top of rule 12 and overrides rule 6: no session merges such a PR before the owner has reviewed and approved it). No release or deployment approval goes through a GitHub environment (C-63): the instance installs only the release the owner approved in the AWS console, and the owner deletes the empty `staging` environment. Agents use the owner's GitHub account (rule 9, C-33, accepted risk R-20); the owner accepted this rule as the control for that risk (C-60). It is a behavioural control and not a technical one, and that residual risk is the owner's. A session that finds a way around this rule must report it to the owner and not use it.
20. Agents never configure, read or use AWS credentials (or Cloudflare's, or those of any other cloud infrastructure or storage provider; the GitHub authentication covered by rule 19 is separate), in any session, on any machine, by any route (CLI, SDK, MCP, environment variables, files). The only AWS writes from GitHub are the release workflow's image push, release record upload and release notice (rule 19, after the owner's review of any change to it); every other AWS change is the owner's, in the AWS console or CloudShell.

Report briefly after each merge, to the owner in chat and in the PR description: what merged, what's next.
